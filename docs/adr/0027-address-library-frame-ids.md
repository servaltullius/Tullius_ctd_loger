# ADR-0027: 게임 프레임에 Address Library ID 붙이기, 후킹 코드에서 끊긴 콜스택 설명

## Status
Accepted (2026-11-09)

## Context
- 2026-11-09 다른 세션(Adaptive Papyrus Budget)의 `coc` 반복 시험에서 같은 지점(SkyrimSE.exe+0xCC90CF)의 크래시가 두 번 났습니다. 그 세션은 Windows가 남긴 전체 덤프를 자체 도구로 풀어, 모든 게임 프레임을 `ID 29895+0xE4`처럼 Address Library ID와 오프셋으로 적었습니다. 모드 제작자는 이 표기로 CommonLib(`REL::ID`)과 바로 대조합니다.
- 우리 리포트는 게임 함수 이름이 내장 DB(약 700개)에 정확히 맞을 때만 이름을 붙여, 같은 콜스택의 대부분이 `SkyrimSE.exe+0x49fb54`처럼 숫자로만 남았습니다.
- 같은 크래시에서 콜스택은 모듈 밖 주소 `0x244c6e94012`에서 끊겼고, 리포트는 "어떤 모듈에도 속하지 않습니다"라고만 했습니다. 그 주소는 Helper가 게임 중 기록한 후킹 페이지(ADR-0024) 안이었고, 페이지의 점프는 `SkyrimSE.exe+0x37F9E6`(ID 23329 안)로 돌아갔습니다. 기록이 덤프에 있었지만 쓰지 않았습니다.
- Address Library 파일은 게임 버전마다 하나이고(1.5.97 `version-1-5-97-0.bin` 형식 1, 1.6.x `versionlib-…` 형식 2, 1.7.104 형식 5), 0.8~2.3MB입니다. MO2에서는 가상 파일 시스템 안에만 있습니다.

## Decision
1. **Helper가 게임 버전의 Address Library 파일을 덤프에 넣습니다.** 게임 실행 파일의 버전으로 파일 이름을 정해(1.5.x는 `version-`, 그 뒤는 `versionlib-`), 게임 폴더의 `Data\SKSE\Plugins`에서 읽습니다. Helper는 게임의 자식 프로세스라 MO2의 가상 파일 시스템으로 게임과 같은 파일을 봅니다. 게임에 붙을 때 한 번 읽어 두고(로그 `Address Library for dumps: N bytes` 또는 없음), 크래시·프리징·수동 캡처의 사용자 스트림 `kMinidumpUserStream_AddressLibrary`("AL")에 원본 그대로 넣습니다. 16MB를 넘거나 없으면 넣지 않습니다.
2. **분석기는 정확히 맞을 때만 ID를 붙입니다.** 형식 1·2(차분 인코딩)와 5(ID 순서의 32비트 오프셋 표)를 풀어 오프셋→ID 표를 만들고, 게임 프레임의 `.pdata` 함수 시작이 어떤 ID의 주소와 정확히 같을 때만 붙입니다: 이름이 있으면 `(TESConditionItem::IsTrue+0x6bc, ID 29924)`, 없으면 `(ID 29895+0xe4)`. 가장 가까운 ID로 어림하지 않습니다(그 함수에 ID가 없으면 다른 함수의 ID가 붙음). 요약 JSON `symbolization.address_library_ids`에 ID 수를 적습니다.
3. **후킹 코드에서 끊긴 콜스택을 설명합니다.** 다음 리턴 주소가 모듈 밖이고 언로드된 모듈 자리도 아니면, 후킹 페이지 기록에서 그 주소가 든 페이지를 찾습니다. 찾으면 근거 항목이 "Helper가 게임 중에 기록한 후킹 코드(모드가 게임 함수를 후킹하며 만든 코드로, 스택 해제 정보가 없음)"라고 말하고, 그 주소 뒤 64바이트 안에 기록된 점프가 있으면 "그 주소에서 21바이트 뒤에 기록된 점프는 SkyrimSE.exe+0x37f9e6 (ID 23329+0x776)(으)로 갑니다"를 덧붙입니다. 기록에는 점프만 있어서 그 주소의 코드가 그 점프까지 이어지는지는 알 수 없습니다(사이에 다른 후킹 코드가 있을 수 있음). 그래서 "이어진다"고 단정하지 않고 다음 점프와 거리를 적습니다. 요약 JSON의 `stackwalk_truncation`에는 `hook_page`, `hook_next_jump`, `hook_next_jump_distance`가 붙습니다.
4. **같은 PR의 표시 정리(#275 검수):** 요약의 프레임 수(`total_frames` 등)는 보이는 콜스택을 셉니다. 보이는 콜스택은 12프레임 구간 앞에 그 위 프레임을 붙여 만들므로 구간 프레임을 두 번 풀지 않습니다. 근거 줄이 맨 위가 아니라 첫 모드 프레임 근처를 보일 때는 제목을 "첫 모드 프레임 주변"으로 씁니다. 크래시 콜스택의 12프레임 구간은 버킷 키·시그니처·표시가 한 상수(`kCrashStackWindowFrames`)를 씁니다.

## Alternatives Considered
- **분석기가 분석할 때 Address Library를 찾기:** MO2에서는 가상 파일 시스템 밖의 분석기가 어느 모드 폴더의 파일인지 알기 어렵고, 덤프를 다른 PC에서 열면 없습니다. 덤프에 넣으면 덤프와 함께 다닙니다(덤프가 2% 남짓 커짐).
- **필요한 ID만 골라 넣기:** 프레임은 분석할 때 정해지고, 캡처 때 스택을 풀어 고르는 일은 크래시 처리 시간을 늘립니다. 파일 전체를 그대로 넣는 편이 단순합니다.
- **가장 가까운 ID로 어림하기:** ID가 없는 함수에 이웃 함수의 ID가 붙어 모드 제작자를 엉뚱한 곳으로 보냅니다.

## Consequences
### Positive
- 게임 프레임 대부분에 ID가 붙어, 모드 제작자가 CommonLib과 바로 대조합니다. 11/09 크래시를 덤프에 스트림을 넣어 다시 분석하자 16개 프레임의 ID와 오프셋이 그 세션의 도구와 모두 같았습니다.
- 후킹 코드에서 끊긴 콜스택이 왜 끊겼는지와, 그 코드에 기록된 다음 점프가 어디로 가는지를 말합니다.
### Limitations
- 이 버전 전의 덤프와, Address Library를 쓰지 않는 환경(파일 없음)에는 ID가 없습니다.
- 후킹 코드의 주인은 말하지 못합니다. 기록에는 그 코드의 점프가 가는 곳만 있습니다.

## Verification
- 분석기: 형식 1·2·5의 합성 바이트, 잘린 파일·모르는 형식·비현실적 개수·남은 바이트보다 큰 개수 거부(`address_library_tests`), 퍼즈 타깃 `fuzz_address_library`(CI에서 60초). 실제 파일 세 종류를 손으로 대조: 1.6.1170 `0x4A05E0` → 29924, 1.5.97 `0xFCFE0` → 11045, 1.7.104 `0x4A7B10` → 29924.
- 후킹 코드 찾기와 근거 문장(`crash_test_findings_tests` `TestStackCutInHookCodeIsExplained`), 표시 프레임 수(`TestCrashStackIsShownFromTheTop`).
- Helper: 파일 이름 규칙, 게임이 아닌 프로세스는 넣지 않음(`helper_hang_runtime_tests`).
- 실제 덤프(11/09 크래시)에 스트림을 덧붙여 다시 분석: 버킷·시그니처·후보는 그대로, 콜스택에 ID, 끊긴 지점 설명.
- 실게임 미확인: 새 Helper가 쓴 덤프에 스트림이 들어가는지, MO2에서 파일을 찾는지.
