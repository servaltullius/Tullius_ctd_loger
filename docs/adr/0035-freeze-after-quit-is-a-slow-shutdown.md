# ADR-0035: 게임의 종료 플래그가 켜진 뒤의 프리징은 느린 종료로 본다

## Status
Accepted (2026-11-17). 구현했고 자동 테스트로 확인했습니다(Verification). 실제 느린 qqq 종료는 실게임에서 아직 보지 못했습니다.

## Context
- 툴챈 제보(v0.2.76 시기, 2026-11-17 00:17): 콘솔 `qqq`로 게임을 끌 때마다 프리징 캡처가 남는다는 내용이었습니다.
  - 리포트 첫 줄: "로딩 화면에서 게임이 멈췄습니다(무한 로딩). 의심되는 모드: usvfs_x64.dll — 가능성 중간".
  - 결론 줄: `capture=hang, heartbeatAge=128.6s >= 127s`, 로딩 중으로 판정. 127초는 그 환경의 적응형 로딩 기준값이므로, 캡처 순간 플러그인의 로딩 플래그(`kState_Loading`)가 켜져 있었습니다.
  - 제보자는 Faster USVFS 알파5를 원래 `usvfs_x64.dll`로 되돌린 직후부터 이런 캡처가 생겼다고 했습니다. qqq 뒤에도 게임 프로세스가 2분 넘게 살아 있었다는 뜻이고, 종료 자체가 실제로 느렸습니다.
- 이때까지의 느린 종료 규칙:
  - `MayBeSlowShutdown`: 메뉴 플래그가 켜져 있고 로딩이 아닐 때 찍힌 캡처만 보류합니다. 게임이 종료 코드 0으로 끝나면 덤프를 지웁니다(`KeepSlowShutdownHangDumps=1`이면 남김).
  - 스레드가 하나만 남은 게임은 캡처하지 않습니다(`IsGameProcessClosing`).
  - 캡처 뒤 게임이 종료 과정에 들어간 것이 보이면, 정상 종료 때 뷰어만 띄우지 않습니다.
  - 로딩 플래그가 켜진 캡처는 셋 다 해당하지 않아, 곧바로 분석되고 크래시 이력에 남았습니다.
- 확인한 것:
  - 1.6.1170 SkyrimSE.exe(Ghidra): 콘솔 명령 `QuitGame`(짧은 이름 `qqq`)의 실행 함수 `0x14036be70`은 콘솔에 "Bye."를 찍고 `Main+0x10`(`Main::quitGame`)을 1로 바꾸는 일만 합니다.
  - 플러그인은 그 플래그를 하트비트 스케줄러 스레드에서 25ms마다 읽어, 켜지는 순간을 블랙박스에 종료 요청(`game_quit` 또는 `forced_quit`)으로 남깁니다(ADR-0022). 이 스레드는 메인 루프가 멈춰도 돕니다.
  - Helper의 프리징 판정은 이 기록을 읽지 않았습니다(크래시 분류에만 씀).
  - 이 PC에서 2026-11-17 15:59에 qqq로 끈 세션: Engine Fixes의 빠른 종료라 1초 안에 종료 코드 0으로 끝났고, 프리징 캡처도 종료 요청 줄도 없었습니다. 종료 요청 줄이 없는 것은 종료가 샘플러보다 빨랐기 때문으로 보이며, 이 환경에서는 제보 상황이 재현되지 않습니다.
- 확인하지 못한 것: 로딩 플래그가 켜진 이유(종료 과정이 LoadingMenu를 여는지, 다른 모드가 종료할 때 로딩 화면을 띄우는지), 제보 덤프의 이벤트 기록, 제보 환경의 종료 코드.

## Decision
1. Helper 루프가 블랙박스를 이어 읽다가 종료 플래그로 생긴 종료 요청(`game_quit`, `forced_quit`)을 처음 보면 그 세션 동안 기억합니다(`QuitRequestWatcher`, `HangCaptureState::gameQuitRequested`). 로그에 `The game was asked to quit (…)` 줄을 남깁니다.
   - 읽는 즉시 기억하는 이유: 블랙박스는 500개짜리 링이라, 긴 종료 중의 스레드 종료 이벤트가 종료 요청을 밀어낼 수 있습니다.
   - Alt+F4 키 기록, 창 닫기, 창에 온 닫기 요청은 넣지 않습니다. 게임이 종료 플래그를 세우지 않았을 수 있고, 멈춘 게임에 누른 Alt+F4도 기록됩니다. 종료 플래그는 게임의 메인 루프가 돌아야 켜지므로, 그 뒤의 멈춤은 종료입니다.
2. 그 뒤에 확정된 프리징은 메뉴·로딩 플래그와 상관없이 느린 종료 후보(`MayBeSlowShutdown`)로 봅니다. 기존 보류 규칙을 그대로 따릅니다.
   - 종료 코드 0으로 끝나면 덤프와 딸린 파일을 분석 전에 지우고, 종료 뒤 뷰어도 띄우지 않습니다.
   - 다른 종료 코드(작업 관리자로 끝낸 게임 등)이면 덤프를 남기고 분석합니다.
   - 보류 로그 줄은 "the game was asked to quit before this freeze"라고 이유를 적습니다.
3. 분석기도 같은 기록을 봅니다. 예외가 없는 프리징 덤프의 블랙박스에 종료 플래그 기록이 있으면(`DetectSlowShutdown`) "느린 종료"로 분류합니다.
   - 빠른 답: 경우 `slow_shutdown`/`freeze_after_quit`, 제목 "게임 종료(메뉴의 종료나 콘솔 qqq)를 고른 뒤 게임이 꺼지는 데 오래 걸린 것입니다. 플레이 중 멈춘 프리징이 아닙니다.", 해볼 일 "따로 할 일은 없습니다…". 의심 모드를 짚지 않습니다. `forced_quit`이면 "게임을 강제로 끈(Alt+F4 등) 뒤…".
   - 결론 문장 앞에 같은 문장을 붙이고, 근거 첫 항목과 `[느린 종료]` 권장(다음 조치 순위 0)을 더합니다. 프리징 분석과 후보는 그 아래에 그대로 둡니다(종료 중 무엇이 돌고 있었는지).
   - 리포트 `분류: 느린 종료 (플레이 중 프리징 아님; game_quit)`, 요약 JSON `analysis.is_slow_shutdown`, `quit_before_freeze.kind`. 뷰어는 분류 줄, 요약 카드, 공유 텍스트 머리말과 유형 줄(`SLOW_SHUTDOWN`)을 "느린 종료"로 씁니다.
   - 프리징인지는 분석기의 판정(`DetermineHangLike`) 하나를 따릅니다. 느린 종료로 판정한 캡처는 요약의 `is_hang_like`도 참이고 `is_snapshot_like`는 거짓입니다.
   - 크래시 이력과 버킷 통계에서 뺍니다(강제 종료와 같음).
4. Helper의 두 링 감시자(`SaveLoadWatcher`, `QuitRequestWatcher`)는 같은 커서(`BlackboxCursor`)로 링을 읽습니다.

## Consequences
- qqq나 메뉴의 종료 뒤 2분 넘게 걸린 종료가 "무한 로딩" 리포트와 크래시 이력으로 남지 않습니다.
- 종료 코드 0으로 끝난 느린 종료는 무엇이 느렸는지 덤프가 남지 않습니다. 남기려면 `KeepSlowShutdownHangDumps=1`입니다.
- 이미 찍힌 그런 덤프도 이 버전의 분석기로 다시 분석하면, 블랙박스에 종료 플래그 기록이 남아 있을 때 "느린 종료"로 나옵니다. 제보자의 덤프에 그 기록이 있는지는 확인하지 못했습니다. 긴 종료 중 기록이 링에서 밀려난 덤프는 그대로 "프리징"입니다.
- 종료 플래그 뒤에 진짜 교착이 생겨 작업 관리자로 끈 경우도 분석기는 "느린 종료"라고 합니다. 종료 중의 교착과 느린 종료를 덤프만으로는 가르지 않습니다.
- 종료 플래그 기록이 빠지는 경우: 샘플러가 플래그를 읽기 전에 끝나는 종료(Engine Fixes의 빠른 종료처럼)는 프리징 기준 시간까지 가지도 않으므로 상관없습니다. 프리징 기준을 넘길 만큼 긴 종료에서는 25ms 샘플러가 읽을 시간이 충분합니다.
- 플러그인과 공유 메모리 형식은 바뀌지 않습니다(이미 남기던 기록을 Helper가 읽을 뿐). 예전 플러그인과 짝지어도 동작합니다(v0.2.70부터 종료 플래그를 기록).

## Verification
- `skydiag_save_load_record_tests`(`TestQuitRequestWatcher`): `game_quit`과 `forced_quit`만 셈(Alt+F4 키, 창 닫기, 닫기 요청은 아님), 아직 쓰이지 않은 항목은 다음에 읽음, 한 번만 알림, 링이 한 바퀴 돈 뒤에도 기억(새로 시작한 감시자는 못 찾음), 다시 시작한 Helper가 링에 남은 요청을 찾음, 레이아웃이 없거나 다른 경우.
- `skydiag_helper_hang_runtime_tests`:
  - 종료 플래그 뒤 로딩 플래그가 켜진 캡처가 보류되고, 종료 코드 0에서 덤프·WCT·매니페스트가 지워지며 뷰어도 남지 않음. `forced_quit` 뒤 플레이 중 캡처도 같음.
  - 종료 코드 1이면 덤프가 남고 분석으로 넘어감.
  - 종료 플래그 없이 로딩 플래그만 있거나 Alt+F4 키 기록만 있으면 전과 같이 곧바로 분석하고 덤프를 남김.
  - `MayBeSlowShutdown`의 정적 확인에 종료 플래그 경우를 더함.
- `skydiag_helper_hang_runtime_tests`(`TestRunHelperLoop_AFreezeAfterAQuitIsASlowShutdown`): Helper 루프가 직접 `game_quit`을 읽고, 로딩 플래그가 켜진 프리징을 보류한 뒤 정상 종료에서 지웁니다.
- `skydiag_quick_answer_tests`(`TestFreezeAfterQuitIsASlowShutdown`): 빠른 답, 결론 앞머리, 근거 첫 항목, 다음 조치, 요약 JSON, 리포트 줄, `forced_quit` 문구, 블랙박스에서의 판정(종료 플래그 종류만, 가장 새 것), 예외·정상 종료 증거가 있거나 프리징이 아니면 판정하지 않음, 크래시 이력에서 빠짐.
- `skydiag_close_request_tests`, `skydiag_recommendation_class_tests`: `IsQuitFlagCloseRequest`, `[느린 종료]` 태그.
- `skydiag_share_text_fixture_tests`(`test_slow_shutdown_is_not_shared_as_a_freeze`): 공유 텍스트의 머리말·유형 줄·다음 조치, 뷰어의 분류 줄과 요약 카드(하네스의 `classification` 모드, 강제 종료도 같이 확인).
- `skydiag_save_load_record_tests`(`TestBlackboxCursor`): 한 바퀴 돌았음을 알림(한 번만), 뒤 바퀴가 이미 쓴 칸은 건너뜀, 한 바퀴에 끝이 사라진 세이브 불러오기를 뒤의 끝으로 잇지 않음.
- Helper 쪽 변이 7개를 모두 잡았습니다: 판정이 종료 플래그를 무시, 보류가 무시, 에피소드 판정이 무시, 루프가 세션에 표시하지 않음, Alt+F4 키를 종료 플래그로 셈, `forced_quit`을 빼먹음, 아직 쓰이지 않은 항목을 건너뜀.
- 검수 수정 뒤 변이 11개도 모두 잡았습니다: 루프가 종료 요청을 읽지 않음, 커서가 바퀴를 알리지 않음·뒤 바퀴 칸에서 멈춤·쓰는 중인 칸을 건너뜀, 분석기가 크래시나 프리징 아닌 캡처에도 판정·크래시 이력에 남김·아무 종료 요청이나 셈, 빠른 답이 무시, 다음 조치가 아님, 요약 JSON 항목 빠짐.
- 보관 덤프 비교(`scripts/compare_analyses.py`, v0.2.77 분석기 대비, 덤프 75개의 한·영 150건): 바뀐 것 없음. 보관 덤프 중에는 종료 플래그 뒤의 프리징이 없습니다.
- 두 번째 검수 수정의 변이 4개 중 3개를 잡았습니다(요약 플래그가 판정을 무시, 공유 텍스트 유형 줄, 뷰어 분류 줄). 공유 텍스트의 `isHangLike`에서 느린 종료를 빼지 않는 변이는 결과가 같은 변이입니다(쓰는 곳마다 느린 종료를 먼저 봄).
- Windows ctest 122/122, WSL 88/88, clang-tidy(CI 스크립트와 Windows) 경고 없음.
- 실게임 미확인: 실제로 기준 시간보다 오래 걸린 qqq·메뉴 종료에서 보류와 삭제가 일어나는 것. 이 PC는 Engine Fixes의 빠른 종료라 재현되지 않습니다.
