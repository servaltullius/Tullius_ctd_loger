# ADR-0034: 모드가 없는 콜스택은 스택 스캔으로 넘기지 않고, 포인터를 덮은 글자와 스크립트 로더를 알린다

## Status
Accepted (2026-11-17). 구현했고 자동 테스트와 실제 크래시 덤프 재분석으로 확인했습니다(Verification).

## Context
- 2026-11-17 01:56과 01:59에 게임 시작 약 54초 만에(메인 메뉴를 불러오는 중) 같은 크래시가 두 번 났습니다.
  - 예외 위치: `SkyrimSE.exe+0x143e7dd`(AE ID 104661+0x2ed), `mov byte ptr [rbx+rax], 0`. 접근 주소를 알 수 없는 일반 보호 오류였고, `rbx=0x138D`, `rax=0x2065726120736C6C`였습니다.
  - 크래시 근처 오브젝트: `SkyrimScript::Store`(RCX), `BSScript::CompiledScriptLoader`(RSP+60), `BSScript::LinkerProcessor`(RSP+400). Papyrus 스크립트를 읽는 중이었습니다.
- 원인은 개발 중이던 모드의 스크립트(.pex) 하나였습니다(직접 확인).
  - 이 스크립트의 설명 문자열(docstring)은 5005바이트였습니다.
  - `rax`의 8바이트를 메모리 순서로 읽으면 글자 "lls are "입니다. 이 글은 그 설명 문자열의 4096번째 바이트부터 이어지는 8바이트와 같습니다. 크래시 스레드의 스택에도 그 설명문 조각이 복사돼 있었습니다.
  - 게임이 .pex의 문자열을 4096바이트 버퍼에 담다가 넘쳤고, 넘친 글자가 옆 변수를 덮었으며, 게임이 그 값을 주소로 쓰다가 튕긴 것으로 봅니다.
  - 사용자가 설명문을 줄여 다시 컴파일한 뒤에는 같은 크래시가 나지 않았습니다.
- 그런데 리포트는 "의심되는 모드: Animation Queue Fix — 가능성 낮음"이라고 했습니다.
  - 정식 콜스택은 스레드 시작점(KERNEL32, ntdll)까지 14개 게임 프레임으로 끝났고, 모드 프레임이 하나도 없었습니다. 분석기는 이것을 "쓸 만한 모듈 없음"으로 보고 원시 스택 스캔으로 넘어갔습니다.
  - 스캔은 Engine Fixes(점수 36, 메모리 할당기 tbbmalloc)와 Animation Queue Fix(점수 2)의 주소를 찾았습니다. 둘 다 콜스택의 반환 주소가 아니라, 스택 슬롯에 남아 있던 이전 호출의 값이었습니다(Crash Logger도 같은 값을 `[S]` 스택 스캔 프레임으로만 보였습니다).
  - 첫 크래시에서 Animation Queue Fix는 스택 분석만으로 행동 우선 후보(낮음)가 됐고, 두 번째에는 같은 자리의 같은 주소가 "반복 이력"으로 더해졌습니다. 같은 크래시는 같은 찌꺼기를 남기므로, 반복은 독립된 근거가 아닙니다.
  - ADR-0015는 "정식 스택 해제가 스레드 시작까지 끝났고 플러그인 프레임이 모두 스레드 입구 훅이면 스캔하지 않는다"고 정했습니다. 플러그인 프레임이 아예 없는 경우는 그 규칙에 들지 않았습니다.
- 사람이 원인을 찾은 단서 두 가지(레지스터 값이 글자라는 것, 스크립트 로더 안이라는 것)를 리포트는 말하지 않았습니다.

## Decision
1. **모드가 없는 완전한 콜스택은 스택 스캔으로 넘기지 않습니다.**
   - 조건(`policy::SkipStackScanAfterCompleteWalk`)
     - 정식 스택 해제가 스레드 시작까지 끝났습니다(DbgHelp가 스스로 끝낸 경우, ADR-0015와 같은 판정).
     - 모든 프레임이 게임 exe, 시스템 모듈, 또는 스레드 입구 훅입니다(`NoPluginOnCompleteWalk`). 어느 모듈에도 속하지 않는 프레임은 모드의 후킹 코드일 수 있으므로 플러그인으로 칩니다. SKSE 런타임 프레임도 플러그인으로 칩니다.
     - 그 콜스택이 예외가 난 스레드의 것입니다.
     - 프리징이 아닙니다. 프리징의 메인 스레드 스캔은 이미 "약한 단서"라고 밝히고 남겨 둡니다.
   - 이때 진단 줄은 `[Stackwalk] complete walk through game and system code only, so no stack scan`입니다.
   - 스택 스캔이 없으면 그 스캔에서 나온 후보도, 그 후보에 붙던 반복 이력도 없습니다. Crash Logger 프레임, 오브젝트 참조 같은 다른 근거로 생긴 후보는 그대로입니다.
2. **포인터 자리를 덮은 글자를 보여 줍니다**(`FaultInstruction`, ADR-0019 보완).
   - 판정이 `noncanonical`(주소가 될 수 없는 값)일 때, 피연산자의 기준 레지스터를 먼저, 그다음 인덱스 레지스터 값을 봅니다.
   - 8바이트를 메모리 순서(리틀 엔디언)로 읽어 모두 출력 가능한 ASCII(0x20~0x7E, 탭·줄바꿈·CR)이거나, UTF-16 네 글자(각 글자가 그 범위이고 윗바이트가 0)이면 글자로 봅니다(`RegisterValueAsText`). 이런 값은 그 자체로 주소가 될 수 없는 값입니다(윗바이트가 0도 0xFF도 아님).
   - 출력
     - 근거 문장: "rax 값을 바이트로 읽으면 글자 "lls are "입니다. 글(문자열)이 포인터 자리를 덮어쓴 것으로 보입니다. 모드 폴더의 파일에서 이 글을 찾으면 그 글이 나온 파일(스크립트, 설정 파일 등)을 알 수 있습니다."
     - 빠른 답의 "어떻게 튕겼나": "포인터 자리를 글("lls are ")이 덮어썼고, 그 값을 주소로 쓰다가 튕겼습니다(메모리 손상)."
     - 리포트의 예외 명령어 줄 뒤: `(rax 값은 글자 "lls are ")`
     - 요약 JSON `fault_instruction.overwritten_text`, `overwritten_text_register`
     - 백슬래시, 큰따옴표, 탭, 줄바꿈, CR은 `\\ \" \t \n \r`로 적습니다.
3. **Papyrus 스크립트 로더 안의 크래시를 알아봅니다**(시그니처 `PAPYRUS_SCRIPT_LOAD`).
   - 조건: 접근 위반(0xC0000005), 예외 모듈 `SkyrimSE.exe`, 크래시 근처 오브젝트(덤프 오브젝트 또는 이 크래시와 짝지어진 Crash Logger 로그)에 `BSScript::CompiledScriptLoader`가 있을 것. 게임 버전은 가리지 않습니다(RTTI 이름은 SE와 AE가 같음).
   - 범위는 `mechanism`, 신뢰도는 중간입니다. 정확한 크래시 지점 시그니처들 뒤, 일반 메커니즘(`CPP_BAD_ALLOC`, `ACCESS_VIOLATION_NULL` 등) 앞에 둡니다.
   - 권장 조치(새 태그 `[알려진 크래시 메커니즘]`/`[Known crash mechanism]`, 지금 바로 묶음): 최근에 추가하거나 업데이트한 모드와 새로 컴파일한 스크립트부터 하나씩 끄거나 되돌리기. 레지스터 값이 글자로 나왔다면 그 글로 .pex를 검색하기. 스크립트를 만든다면 문자열을 4096바이트보다 짧게 하기.
   - 다음 조치 순위에서 이 태그는 7입니다. 모드 단위 줄(행동 우선 후보·유력 후보 4, Crash Logger 프레임 5, 오브젝트 참조 6)보다 뒤라서 빠른 답이 모드를 지목하면 그 모드가 먼저이고, 두 모드가 같은 파일을 제공한다는 `[충돌]`(8)보다는 앞입니다. 처음 만든 판(`[점검]`, 순위 없음)으로 다시 분석했을 때는 다음 조치가 메뉴 로고 메시의 `[충돌]`로 가서 빠른 답과 어긋났습니다. 뷰어가 예전 요약에만 쓰는 태그 목록(`next_action_index`가 없는 요약)은 이 태그를 만날 일이 없어 바꾸지 않았습니다.
4. **모드를 특정하지 못한 크래시에서는, 자기 제목(headline)이 있는 메커니즘 시그니처가 빠른 답을 채웁니다.**
   - 지금은 `PAPYRUS_SCRIPT_LOAD`만 제목이 있습니다. 제목이 없는 메커니즘(FaceGen, `ACCESS_VIOLATION_NULL` 등)의 빠른 답은 그대로입니다.
   - 빠른 답
     - 제목: "게임이 튕겼습니다(CTD). Papyrus 스크립트(.pex)를 읽는 중이었던 것으로 보입니다. 원인 모드는 특정하지 못했습니다."
     - 해볼 일: 시그니처의 첫 권장 조치 첫 문장
     - 확실하지 않은 이유: 시그니처의 `why_not_certain`
     - 경우(case): `known_mechanism`
   - 모드를 지목한 빠른 답은 바꾸지 않습니다. 메커니즘은 결론 문장과 근거에만 나옵니다.

## Consequences
- 2026-11-17의 두 덤프를 다시 분석한 결과
  - 빠른 답: 위 제목, "최근에 추가하거나 업데이트한 모드와 새로 컴파일한 스크립트(.pex)부터 하나씩 끄거나 이전 파일로 되돌려 보세요.", "포인터 자리를 글("lls are ")이 덮어썼고…"
  - 후보 0개. Animation Queue Fix와 Engine Fixes는 나오지 않습니다.
- 모드가 데이터를 망가뜨리고 자기 코드를 떠난 뒤 게임 코드에서 튕긴 크래시는, 이제 스택 스캔 후보 없이 "원인 모드는 특정하지 못했습니다"가 됩니다. 이전에는 그 경우 스캔이 찾은 모드가 "가능성 낮음"으로 첫 줄에 올랐는데, 그 모드가 원인이라는 근거는 스택 슬롯에 남은 값뿐이었고 이번처럼 엉뚱한 모드일 수 있었습니다. Crash Logger의 오브젝트 참조나 크래시 이력처럼 스캔이 아닌 근거는 그대로 남습니다.
- 글자 판정은 ASCII와 UTF-16의 ASCII 범위만 봅니다. UTF-8 한글처럼 여러 바이트 글자가 8바이트 경계에 걸친 값은 알아보지 못합니다.
- 스크립트 로더 판정은 오브젝트 하나가 근처에 있다는 것에 기댑니다. 덤프 오브젝트는 레지스터와 RSP부터 2KB의 스택에서 읽으므로 오래된 값일 수 있어 신뢰도를 중간으로 두었습니다. "4096바이트가 넘는 문자열" 예는 이번 한 사례에서 바이트 단위로 확인한 것이고, 그 밖의 스크립트 로더 크래시 원인은 확인하지 않았습니다.
- 빠른 답의 경우 값 `known_mechanism`이 새로 생깁니다. 뷰어는 경우 값을 따로 쓰지 않습니다.

## Verification
- 자동 테스트
  - `skydiag_fault_instruction_tests`: 이번 명령어와 레지스터(`C6 04 03 00`, rbx=0x138D, rax=0x2065726120736C6C)의 글자·근거 문장·쉬운 문장·리포트 줄, 기준 레지스터 우선, 글자가 아닌 값(2026-10-05 CrashLogger.dll 모양)은 그대로, `RegisterValueAsText`의 ASCII·UTF-16·이스케이프·거부 경우
  - `skydiag_thread_entry_hook_tests`: `NoPluginOnCompleteWalk`(이번 모양, 끊긴 스택, ContentCatalog 모양, 게임이 부른 플러그인, 메인 루프 훅, 플러그인 자신의 스레드, 모듈 밖 프레임)
  - `skydiag_scoring_logic_tests`: `SkipStackScanAfterCompleteWalk`의 조건 다섯 가지와 연결
  - `skydiag_analysis_engine_runtime_tests`: 번들 DB의 `PAPYRUS_SCRIPT_LOAD` 일치(AE, SE), 로더 없음·플러그인 안·다른 예외는 불일치, FaceGen 정확한 지점이 먼저
  - `skydiag_quick_answer_tests`: 빠른 답(경우, 제목, 해볼 일, 확실하지 않은 이유, 어떻게 튕겼나), 모드를 지목하면 그대로, 제목 없는 메커니즘은 그대로, 요약 JSON과 리포트 줄
  - 변이 7개(UTF-16 경로, 인덱스 레지스터, 모듈 밖 프레임, 끊긴 스택, 제목 없는 메커니즘, 모드를 지목한 경우, 리포트 줄)를 모두 잡았습니다.
- 실제 덤프: 2026-11-17 01:59 덤프를 새 분석기로 다시 분석해 위 Consequences의 출력을 확인했습니다.
- 보관 덤프 비교(`scripts/compare_analyses.py`, main 74cc64e의 CLI 대 이 변경, 한국어·영어): 보관 덤프 31개와 로그 폴더 덤프 44개, 분석 150건 중 바뀐 것은 2026-11-17 스크립트 로더 덤프 2개의 4건뿐입니다. 스캔을 건너뛰어 후보가 바뀐 덤프도 이 둘뿐이었습니다(다른 덤프는 후보까지 같음). 태그를 바꾼 뒤 로그 폴더 덤프 44개(88건)를 다시 비교했을 때도 같은 4건만 바뀌었고, 다음 조치가 `[알려진 크래시 메커니즘]` 줄이 됐습니다.
