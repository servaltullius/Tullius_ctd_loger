# v0.2.79 — 게임 폴더 프록시 DLL 판정, 뷰어 사용성, 플러그인 설정 읽기와 긴 경로 정리

v0.2.79-rc1\~rc3을 정식으로 내는 릴리즈입니다. rc3 이후에는 배포되는 파일의 코드가 바뀌지 않았습니다(CHANGELOG 날짜만). v0.2.78에서 올리면 플러그인, Helper, 분석기, 뷰어가 모두 바뀝니다(SharedLayout protocol v4 그대로, 새 설정 없음). ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요. v0.2.77 이전 버전에서 바로 올린다면 v0.2.78 노트의 변경도 함께 들어갑니다.

v0.2.78 이전 버전이 분석해 둔 덤프는 뷰어에서 열 때 한 번 다시 분석합니다. rc1\~rc3으로 분석해 둔 덤프는 버전 번호(0.2.79)가 같아서 자동으로 다시 분석하지 않습니다. rc2부터 분석기가 바뀌지 않았으므로 rc2·rc3로 분석한 덤프는 그대로 두면 됩니다. rc1로 분석한 덤프를 지금 분석기로 보려면 뷰어에서 덤프를 고른 뒤 "지금 분석"을 눌러 주세요.

## 한눈에 보기
- **게임 폴더에 놓인, 시스템 DLL과 이름이 같은 모드 DLL을 크래시 후보로 봅니다.** OptiScaler의 `winmm.dll`처럼 게임 폴더에 놓여 Windows DLL 이름을 쓰는 모드 DLL은 System32의 같은 이름 DLL과 함께 올라옵니다. 지금까지 분석기는 이름만 보고 이를 시스템 DLL로 걸러, Crash Logger가 그 DLL 안에서 난 크래시라고 적어도 다른 모드와 "신호가 갈린다"고 했습니다. 이제 실제로 올라온 위치를 보고 모드 DLL로 봅니다.
  - 보관 덤프로 확인했습니다: `winmm.dll` 크래시 덤프 2개(한·영 4건)가 바뀌었습니다. 하나는 결론이 "`winmm.dll`과 다른 DLL 사이에서 신호가 갈림"에서 "`winmm.dll` 안에서 난 크래시(신뢰도 중간), 근처 DLL도 비교"로 바뀌었습니다. 다른 하나는 크래시 위치가 시스템 DLL로 보고된 덤프입니다. 빠른 답이 `winmm.dll`을 "가능성 높음" 의심 모드로 짚던 것이 Crash Logger 프레임을 근거로 한 "가능성 중간" 후보로 바뀌었고, 다음 조치는 "신호 충돌"에서 이 DLL 점검으로 바뀌었습니다.
  - 게임 폴더의 `d3d11.dll`, `dxgi.dll`, `d3d9.dll`, `d3d12.dll`(ENB, ReShade, DXVK 등)은 후보 판정에서는 전부터 경로를 봤습니다. 이제 프리징의 "GPU 대기" 판정과 빠른 답도 이들을 모드 DLL로 봅니다. 아래 주의사항을 봐 주세요.
- **뷰어의 핵심 요약(Triage)을 바로 쓸 수 있게 했습니다.**
  - 요약의 글을 선택해 복사할 수 있습니다.
  - 요약 위에 "Crash Logger 로그 열기", "리포트 폴더 열기" 버튼이 있습니다. "Crash Logger 로그 열기"는 그 덤프와 짝지어진 Crash Logger 로그(`.log`)를 찾았을 때 나타나고, 그 로그를 엽니다.
  - 원시 데이터 탭에 "WCT 복사", "리포트 복사" 버튼이 있습니다.
  - 대시보드 안에 있던 상태 표시를 창 아래쪽 상태 바로 옮겨, 어느 탭에서든 지금 하는 일과 결과가 보입니다.
  - 최근 덤프 목록이 12개에서 30개까지 보입니다. 목록에서 아직 분석하지 않은 덤프를 고르면 최대 1.5초 기다리지 않고 바로 분석을 시작합니다.
- **플러그인이 `SkyrimDiag.ini`를 `SkyrimDiag.dll` 옆에서 직접 읽습니다.** 지금까지는 게임의 작업 폴더 기준 경로로 Windows의 INI 함수가 읽었습니다. 이제 UTF-8(BOM 포함) 파일, 한글 경로, MO2의 긴 경로에서도 읽습니다. `SkyrimDiag.log`에 `loaded config from ...` 또는 `config not found at ...; using defaults` 줄이 남아, 설정을 읽었는지 바로 볼 수 있습니다.
- **출력 폴더 경로가 길어도 오래된 덤프를 지웁니다.** MO2나 게임 폴더를 깊은 곳에 둬서 출력 폴더 경로가 대략 200자를 넘으면, 보존 한도(`MaxCrashDumps`, `MaxHangDumps` 등)를 넘어도 덤프를 지우지 못했습니다(예전부터 있던 문제). 이제 경로 길이와 상관없이 덤프와 그 옆의 부속 파일(인시던트·재캡처 기록, WCT JSON 등)을 함께 지웁니다.
- **사전 점검에 두 항목이 늘었습니다.** `SkyrimDiag_Preflight.json`에 `BINARY_VERSION_CONSISTENCY`(플러그인, 분석기, 뷰어용 분석 DLL의 버전이 Helper와 같은지)와 `ADDRESS_LIBRARY_PRESENT`(실행 중인 게임 버전의 Address Library가 있는지)가 나옵니다. 버전이 섞인 설치를 알아챌 수 있습니다.

## 수정
**플러그인**
- 설정 파일 읽기를 바꿨습니다(위 한눈에 보기). 파일이 없거나 읽지 못하면 기본값을 쓰고 그 사실을 로그에 남깁니다.
- Alt+F4로 게임의 종료 플래그(`Main::quitGame`)가 켜지면, 키 입력 기록과 별도로 종료 플래그 기록을 항상 남기고, Helper와 분석기가 그 기록을 종료 플래그로 인정합니다. 지금까지는 Alt+F4가 눌린 채 켜진 종료 플래그를 일반 Alt+F4로 취급해, 기록 순서와 상관없이 그 뒤의 크래시를 10초 안에서만 강제 종료 중 오류로 판정했고, Helper도 종료 요청을 알아채지 못했습니다(키 입력이 먼저 기록했으면 종료 플래그 쪽은 아무것도 남기지 않았습니다). 이제 메뉴의 종료처럼 시간 제한 없이 판정합니다(v0.2.78의 느린 종료, 종료 플래그 뒤 크래시).
- Helper가 먼저 "처리된 예외"로 놓아준 예외가 결국 아무도 처리하지 않은 크래시가 되면, 그 사실을 Helper에 알립니다. Helper는 게임이 끝날 때 그것을 크래시로 기록합니다. 새 크래시가 생기면 앞 크래시의 신호는 지웁니다.
- 첫 데이터 로드 때 이벤트 감시를 로딩 화면 확인보다 먼저 등록해, 그 사이의 메뉴 변화를 놓치지 않습니다. 하트비트마다 로딩 상태도 다시 맞춥니다.
- 기타: 리소스 훅의 vtable 검사 범위, 원본 함수 포인터를 패치 전에 공개, 스레드 목록 핸들 정리, 세션 로그 보관의 긴 경로 처리, RTTI 이름 읽기 길이 제한.

**Helper**
- 앞의 Helper 둘이 같은 크래시에서 연달아 꺼지거나 재시도 표시 파일을 쓰지 못해 다음 Helper가 그 크래시를 놓아준 경우, 게임이 정상 종료(종료 코드 0)로 끝나면 크래시로 기록하지 않습니다. 지금까지는 정상 종료여도 종료할 때 크래시로 기록할 수 있었습니다. 다른 종료 코드로 끝나면 지금처럼 기록하고, 앞의 Helper가 덤프를 쓰지 못했으면 덤프 없이 기록만 남깁니다.
- 크래시 순간의 오브젝트 메모리를 읽을 때, 살아 있는 게임의 가드 페이지(`PAGE_GUARD`)를 건드리지 않습니다. 건드리면 게임이 쓰는 1회성 보호가 사라질 수 있었습니다.
- 프리징, 수동 캡처, 자동 재캡처 덤프도 크래시 덤프처럼 공유 메모리의 일관된 스냅샷으로 기록합니다. 재캡처 인시던트 기록의 `state_flags`에 실제 값을 씁니다.
- Crash Logger 스레드 덤프 창(1분)에서 더 새 크래시에 밀린 예외는 덤프를 쓰지 않고 새 크래시로 넘어갑니다.
- 그래픽 드라이버 오류(TDR) 조회가 크래시와 같은 초에 난 이벤트를 빠뜨리지 않습니다.
- 보존 정리, 로그 회전, 덤프 식별 파일, Helper 로그 쓰기가 모두 긴 경로를 처리합니다(`PathForIo`). Helper 로그 쓰기는 여러 스레드에서 동시에 써도 섞이지 않습니다.
- 사전 점검 두 항목을 추가했습니다(위 한눈에 보기). 배포 ZIP에서 뷰어용 분석 DLL이 놓이는 `SkyrimDiagWinUI/app` 폴더도 찾습니다.

**분석기**
- 게임 폴더의 시스템 이름 모드 DLL을 실제 경로로 판정합니다(위 한눈에 보기). Crash Logger 스택의 첫 모드 프레임이나 가장 긴 연속 프레임이 그래픽 드라이버나 SKSE·Crash Logger 같은 훅 DLL이라 걸러지면, 그다음 모드 프레임을 다시 찾습니다. 스레드 스택에서 같은 이름의 DLL을 찾을 때도 경로로 구분합니다.
- 메인 스레드가 DirectX에서 기다린 프리징의 "GPU 대기" 판정과 빠른 답이 같은 기준을 씁니다. 게임 폴더의 DirectX 이름 DLL은 GPU 대기가 아니라 모드로 봅니다.
- 예외 명령어 해석: 비정규 주소 접근(`#GP`)에서 쓰기만 하는 명령은 접근 방향을 `write`로 적습니다(지금까지는 `read`). `rep movs*`, `rep stos*`와 AVX/AVX2(VEX) 메모리 명령을 해석합니다.
- WCT에 교착 순환이 하나라도 잡히면, 하트비트가 정상인 수동 캡처도 프리징으로 판정합니다.
- Alt+F4 뒤 종료 플래그로 생긴 강제 종료는 메뉴 종료와 같은 규칙(시간 제한 없음)을 씁니다. 그런 느린 종료는 "Alt+F4" 문구로 나옵니다.
- 그래픽 드라이버 오류 개수, Crash Logger의 `CALL STACK` 구간 끝, 태그가 붙은 MO2 모드 이름의 의심 문구를 고쳤습니다.

**뷰어**
- 핵심 요약(Triage)의 글 선택, 버튼, 상태 바, 최근 덤프 30개(위 한눈에 보기).
- "Crash Logger 로그 열기"는 확장자가 `.log`인 파일만 엽니다(대소문자 무관). 받은 덤프 묶음의 요약 파일이 다른 실행 파일을 가리켜도 실행하지 않습니다.
- 다른 덤프를 빠르게 연달아 골라도 앞 분석의 결과나 "분석 중" 표시가 새 분석을 덮어쓰지 않습니다. 분석 중에는 "리포트 폴더 열기"가 꺼집니다.
- 덤프 폴더를 드라이브 루트(`D:\`)로 골라도 경로가 깨지지 않습니다.
- 분석기가 고른 다음 조치가 일반적인 모달 대화상자 안내보다 먼저 나옵니다. 덤프를 바꾸면 이벤트 개수 표시가 초기화됩니다.
- 블랙박스 이벤트는 마지막 200줄만 해석해 큰 파일도 더 빨리 엽니다. 문제 해결 카드의 제목이 원래 머리글 모양을 유지합니다.

**출력 형식**(바뀐 필드)
- 요약 JSON `forced_close.window_seconds`는 Alt+F4 뒤 종료 플래그로 생긴 강제 종료(`from_quit_flag`)에는 쓰지 않습니다.
- 사전 점검 JSON에 `BINARY_VERSION_CONSISTENCY`, `ADDRESS_LIBRARY_PRESENT` 항목.

**CI·테스트·개발 도구(내부)**
- 크래시 테스터: `Ctrl+Shift+PageUp`(`AutoScenario=15`, C++ `catch` 블록 안의 접근 위반).
- 위 수정마다 회귀 테스트를 붙였습니다. rc3의 수정 테스트는 모두 수정 전 코드에서 실패하는 것을 확인했습니다.
- Linux CI의 패키지 설치 재시도와 미러 폴백, Windows CI의 vcpkg 캐시와 재시도.
- 이 PC처럼 메모리 사용량이 높은 환경에서 `memory_snapshot_e2e` 테스트가 실패하던 것을 고쳤습니다(제품 동작과는 무관).
- 설계 문서 보강: ADR-0022(Alt+F4 뒤 종료 플래그), ADR-0028(WCT 순환이 있는 수동 캡처), ADR-0032(Helper가 먼저 놓아준 크래시의 unhandled 신호와 그 한계).

## RC 사이에 바뀐 것
rc1·rc2에서 생겼다가 rc3에서 고친 문제입니다. v0.2.78에서 바로 올리는 경우에는 해당하지 않습니다.
- rc1·rc2: 앞의 Helper들이 끝내지 못해 다음 Helper가 다시 신호하기를 포기한 크래시 뒤에 게임이 0이 아닌 종료 코드(예: Crash Logger의 1)로 끝나도, 플러그인의 신호가 없으면 기록하지 않았습니다.
- rc2: 출력 폴더 경로가 246자 이상이면 덤프만 지우고 부속 파일을 남겼습니다.
- rc2: 뷰어의 "호환 산출물 폴백"이 이름이 같은 다른 덤프의 리포트·WCT·블랙박스를 보여 줄 수 있었습니다. 이 폴백은 없앴고, 덤프 전용 파일만 읽는 v0.2.78의 동작으로 돌아왔습니다.
- rc2: "Crash Logger 로그 열기"가 확장자를 확인하지 않았습니다.

rc1·rc2 노트에는 코드와 다른 문장이 있었고, rc3 노트에서 정정했습니다. 이 노트는 코드에 맞춰 다시 썼습니다.
- 상태 바는 창의 위가 아니라 아래쪽에 있습니다.
- `d3dcompiler_47.dll`은 게임 폴더에 있어도 지금처럼 시스템 DLL로 봅니다. `d3dx9_42.dll`은 이 변경과 관계없습니다.
- rc1 노트에 시스템 DLL 이름 목록의 예로 든 `dinput8.dll`, `xinput1_3.dll`은 그 목록에 없습니다.
- rc2 노트의 "긴 경로에서 보존 정리가 일관되게 동작"은 rc3에서야 맞게 됐습니다.

## 실게임에서 확인한 것
같은 MO2 환경(게임 1.6.1170, Crash Logger 켬, Engine Fixes의 빠른 종료 켬)에서 확인했습니다.
- **rc3 공개 패키지(2026-11-22)**: 10:06\~21:49에 일곱 번 실행했습니다. MO2 기록상 일곱 번 모두 rc3 모드 폴더의 Helper가 붙었고, 모두 사전 점검 경고·오류 0건, 정상 종료(`exit_code=0`)였습니다. 여섯 번은 세이브를 불러왔습니다. 프리징이나 크래시 캡처는 생기지 않았습니다.
  - `SkyrimDiag.log`(마지막 실행)에 `loaded config from ...\SkyrimDiag.ini`와 `loaded (v0.2.79.0)`이 찍혔습니다.

## 주의사항
- 게임 폴더에 놓인 `d3d11.dll`, `dxgi.dll` 같은 DirectX 이름의 DLL(ENB, ReShade, DXVK 등)을 모드 DLL로 봅니다. 그래서 그래픽 드라이버 프레임 없이 이런 DLL 안에서 멈춘 프리징은 "GPU 대기" 대신 그 DLL을 의심 모드로 짚을 수 있습니다. 이 PC의 게임 폴더에는 그런 DLL이 없어서 실제 덤프로는 확인하지 못했습니다.
- WCT 교착 순환은 Helper가 한 번 훑은 결과입니다. 게임이 돌고 있는데 백그라운드 스레드에 잠깐 잡힌 순환이 있으면 수동 캡처가 프리징으로 나올 수 있습니다. 실제 덤프로 확인한 사례는 없습니다.
- Helper가 먼저 놓아준 크래시의 신호는, 게임이 끝나기 전에 같은 프로세스에서 다른 예외가 새 크래시로 기록되면 지워집니다. 그 경우 새 크래시는 기록되지만, 앞 크래시는 종료 코드 규칙으로만 판정합니다(ADR-0032).
