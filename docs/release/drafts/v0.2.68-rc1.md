# v0.2.68-rc1 — NVIDIA·오버레이 DLL 오지목 수정, 한글 리소스 경로, Crash Logger C++ 예외 누락, 분석 속도

외부 리뷰에서 미뤄 둔 항목을 모두 정리하고, 넥서스 사용자 리포트(NVIDIA DLL 지목)를 고친 테스트용 프리릴리즈입니다. 플러그인과 Helper가 크래시를 기록하는 방식이 바뀌어 실게임 확인이 필요합니다.

## 핵심 변경
- **그래픽 카드 제조사 프로그램과 오버레이 DLL을 모드처럼 지목하지 않습니다.** 넥서스 사용자 리포트에서 NVIDIA 텔레메트리 DLL(`NvTelemetryBridge64.dll`)이 크래시 후보로 나왔습니다. 분석기는 `Windows\System32` 등 Windows 폴더의 DLL만 시스템 모듈로 봤기 때문에, `Program Files\NVIDIA Corporation` 아래 DLL이나 Steam·Discord 오버레이 DLL은 SKSE 플러그인과 똑같이 후보가 되고 "모드를 꺼 보라"는 안내를 받았습니다.
- **프리징 결론이 WCT 데드락·로딩 정지 판정과 어긋나지 않습니다.** 메인 스레드가 게임 엔진 안에서 대기 중이면, Windows 대기 체인(WCT)이 스레드 간 순환을 찾았거나 로딩 중 정지로 판정했어도 결론 문장은 "엔진이 무엇을 기다렸는지 이 덤프만으로 알 수 없음(신뢰도 낮음)"이라고 적었습니다. 권장 조치와 판정 근거는 이미 데드락·로딩 정지를 먼저 다루고 있었습니다.
- **긴 세션에서도 프리징의 메인 스레드를 찾습니다.** 플러그인이 하트비트 이벤트를 한 번도 기록하지 않아, 블랙박스 이벤트가 65,536개를 넘어 세션 시작 기록이 밀려나면 Helper와 분석기가 메인 스레드를 알아내지 못했습니다(프리징 분석과 덤프의 메인 스레드 우선 수집이 이 판단에 기댑니다).
- **한글 등 비ASCII 이름의 메시·애니메이션 경로를 제대로 기록합니다(감사 F16).** 게임은 리소스 경로를 Windows ANSI 코드 페이지(한국어 Windows는 CP949)로 넘기는데, 플러그인은 그 바이트를 UTF-8로 간주해 저장했고, 대문자를 소문자로 바꾸는 처리가 CP949 글자의 두 번째 바이트까지 바꿔 다른 글자가 됐습니다. 리포트에 깨진 파일 이름이 나오고 그 파일을 제공한 MO2 모드도 찾지 못했습니다.
- **MO2 프로필 이름이 한글이어도 분석 시점 대체 경로가 그 프로필을 읽습니다.** MO2는 이런 이름을 `ModOrganizer.ini`에 `\xNN` 이스케이프로 적는데, Helper가 크래시 때 기록한 정보가 없는 덤프를 분석할 때는 이를 풀지 않아 다른 프로필을 골랐습니다.
- **게임 시작 시간을 로딩 화면 시간으로 세지 않습니다.** Helper는 로딩 화면 시간을 모아 무한로딩 판정 기준을 자동으로 정하는데, 게임을 켤 때 데이터를 읽는 2분 남짓도 로딩 한 번으로 기록했습니다. 실제 기록(세이브 로딩 23~26초, 게임 시작 124~149초)에서 기준이 약 269초로 부풀어, 무한로딩을 늦게 알아챘습니다. 이제 처음부터 끝까지 본 로딩 화면만 셉니다(같은 기록이면 약 146초). 이미 저장된 시작 시간 기록은 새 로딩이 쌓이며 밀려납니다.
- **`LogMenus=0`이어도 로딩·메뉴 상태를 추적합니다.** 이 설정은 메뉴 이벤트를 블랙박스에 남기지 않는 옵션인데, 메뉴 감시 자체를 꺼서 로딩 화면이 로딩으로 인식되지 않았고(짧은 일반 프리징 기준이 적용됨), 시작 때 켜 둔 로딩 상태가 꺼지지 않을 수 있었습니다.
- **Crash Logger가 보고하는 처리되지 않은 C++ 예외를 다른 스레드의 잡힌 예외가 가리지 않습니다.** 플러그인은 이런 예외를 슬롯 하나에 보관했다가 Crash Logger가 그 스레드에서 보고할 때 기록하는데, 그 사이 다른 스레드에서 잡히는 C++ 예외가 나면 슬롯을 덮어써 진짜 크래시가 무시되고 덤프가 아예 생기지 않았습니다.
- **모드가 많은 환경에서 분석이 훨씬 빨라졌습니다.** 최근 리소스마다 그 파일을 가진 MO2 모드를 찾으면서, 파일 하나에 켜진 모드 전체를 디스크에서 확인했습니다. 켜진 모드 4,362개, 최근 파일 110개인 수동 캡처 하나가 약 48만 번 확인하느라 분석에 11~15초 걸렸는데, 이제 1초입니다(결과는 같음).

## 엔진 변경
- 분석기: 다음을 "외부 프로그램"으로 분류합니다. 파일 이름으로 NVIDIA 텔레메트리·캡처(`NvTelemetryBridge64.dll`, `NvTelemetryAPI64.dll`, `NvTelemetry64.dll`, `nvspcap64.dll`), Steam 오버레이(`GameOverlayRenderer64.dll`), Discord 오버레이(`DiscordHook64.dll`), RivaTuner Statistics Server(`RTSSHooks64.dll`), OBS 게임 캡처(`graphics-hook64.dll`). 설치 폴더로 `Program Files`(x86 포함) 아래 `NVIDIA Corporation`, `AMD`, `Intel`. Windows 폴더에 있는 사본은 지금처럼 시스템 모듈입니다.
- 외부 프로그램 DLL은 콜스택·스택 스캔 후보, Crash Logger 콜스택 단서, 선행 예외(first-chance) 후보에서 빠집니다. Crash Logger 로그에는 경로가 없어 이름 목록으로 거릅니다.
- 예외가 외부 프로그램 DLL 안에서 났다면 결론에 "외부 프로그램(NVIDIA, NvTelemetryBridge64.dll)"이라고 적고, 권장 조치는 모드 선행 조건 확인 대신 그 프로그램(그래픽 카드라면 드라이버와 그 앱)의 업데이트·재설치, 오버레이 끄기를 안내합니다. 콜스택에 모드 DLL이 있으면 그 후보를 지금처럼 함께 보여 줍니다. 요약 JSON `exception.external_software`.
- 분석기: 프리징 판정이 데드락(`deadlock_likely`)이나 로딩 정지(`loader_stall_likely`)면 결론 문장이 그 판정으로 시작하고, 신뢰도는 프리징 판정의 신뢰도를 씁니다. 스택 후보는 엔진 안에서 기다리던 메인 스레드의 스택이 아닐 때만(예: 순환에 든 다른 스레드) 함께 적습니다. 판정이 없어도 후보가 메인 스레드가 아닌 스레드에서 나왔다면 "엔진 대기" 문장 대신 그 후보를 적어, 후보 목록과 맞춥니다.
- 플러그인: 메인 스레드 작업에서 60초마다 하트비트 이벤트를 남깁니다.
- Helper·분석기: 메인 스레드를 가장 최근 하트비트, 세션 시작, 메인 스레드에서 기록되는 히치·메뉴·로딩 이벤트 순으로 찾습니다. 하트비트가 없는 이전 덤프도 세션 시작이 밀려났다면 메뉴·로딩 이벤트로 찾습니다.
- 플러그인: 리소스 경로에 0x80 이상 바이트가 있으면 ANSI 코드 페이지에서 UTF-8로 바꾼 뒤 정규화하고, 260바이트에서 자를 때 글자 중간에서 자르지 않습니다. 순수 ASCII 경로는 지금과 같습니다(해시 값도 같음).
- 분석기: UTF-8이 아닌 리소스 경로(이전 버전 덤프)는 ANSI 코드 페이지로 읽습니다. 이미 소문자 처리로 바뀐 글자는 되돌릴 수 없습니다.
- 분석기: `selected_profile`을 Helper와 같은 QSettings 해석기(`DecodeQSettingsIniValue`, 공용 헤더로 옮김)로 읽습니다.
- 플러그인: 로그 폴더 이름에 ANSI 코드 페이지로 나타낼 수 없는 글자(예: 영어 Windows의 한글 사용자 이름)가 있으면 8.3 짧은 이름으로 로그를 엽니다. 짧은 이름도 없으면 지금처럼 로그 없이 동작합니다. Helper 경로가 없을 때 남기는 경고 줄이 이런 경로에서 예외를 던져 게임이 종료될 수 있던 문제도 고쳤습니다.
- Helper: 게임이 로딩 중일 때 연결되면(게임 시작) 그 로딩 시간을 통계에 넣지 않습니다.
- 플러그인: 메뉴 감시는 항상 등록하고, `LogMenus`는 메뉴·로딩 이벤트를 블랙박스에 쓸지만 정합니다.
- Helper: 정상 종료(종료 코드 0) 때 "잡힌 1차 예외를 처리된 것으로 본다"는 로그 줄을, 실제로 잡힌 예외가 있었을 때만 남깁니다.
- Helper: 자동 재캡처(`EnableAutoRecaptureOnUnknownCrash=1`, 기본 꺼짐)로 만든 전체 덤프와 그 기록 파일을, 원래 크래시가 정상 종료나 늦은 복구로 걸러질 때 함께 정리합니다(늦은 복구면 덤프는 남김). 이전에는 처리된 예외의 전체 덤프와 "CTD" 리포트가 남았습니다. 재캡처 덤프를 분석하던 프로세스는 추적하지 않아, 정리 뒤에 끝나면 리포트가 덤프 없이 남을 수 있습니다.
- 뷰어: 검토 피드백을 저장하면 출력 폴더의 `<덤프 이름>_SkyrimDiagSummary.json`에도 반영합니다(그 파일이 같은 덤프의 것일 때만). 이전에는 뷰어가 쓰는 분석 캐시 쪽 요약에만 들어가, 다시 분석하기 전까지 공유하는 요약 파일에는 빠져 있었습니다.
- 뷰어: "지금 분석"을 빠르게 두 번 누르면 두 분석이 엇갈려 먼저 고른 덤프의 결과가 남을 수 있던 문제를 고쳤습니다.
- 플러그인: 처리되지 않은 중단점·C++ 예외를 스레드마다 따로 보관합니다(8칸, ADR-0017). 마지막으로 기록한 크래시보다 먼저 보관된 예외는 Crash Logger 탐침 때 쓰지 않습니다.
- 크래시 테스터(개발용): F3은 다른 스레드가 C++ 예외를 계속 던지고 잡는 동안 실행합니다. Ctrl+Shift+F5(스스로 잡는 접근 위반 2초 뒤 진짜 접근 위반)는 아래 남은 한계를 재현합니다.
- 분석기: MO2 제공 모드를 찾을 때 모드마다 폴더(`meshes`, `meshes\actors` …)가 있는지를 한 번만 확인해 기억하고, 그 폴더가 없는 모드는 그 아래 모든 파일에서 바로 뺍니다. 실제 덤프 37개의 결론·후보·제공 모드는 바뀌지 않았습니다.
- 뷰어: 새 안내 `[외부 프로그램]`을 "지금 바로" 묶음에 보여 줍니다.

## 테스트 시 확인할 점
- 평소처럼 플레이하고 `Ctrl+Shift+F12`로 수동 캡처를 한 번 해 주세요. 리포트와 뷰어가 이전처럼 나오면 됩니다. 분석이 이전보다 훨씬 빨리 끝나야 합니다.
- `SkyrimDiag.log`에 로그가 정상으로 쌓이는지(플러그인 로그 경로 처리 변경) 봐 주세요.
- 개발용 크래시 테스터가 있다면 테스트용 세이브에서:
  - `Ctrl+Shift+F3`(Crash Logger 설치 상태): 다른 스레드가 C++ 예외를 계속 던지는 동안의 처리되지 않은 C++ 예외. 크래시 덤프가 생겨야 합니다.
- CTD가 나면(일부러 낼 필요는 없습니다) 리포트와 뷰어가 이전처럼 나오는지 봐 주세요.

## 주의사항
- 플러그인, Helper, 분석기, 뷰어가 모두 바뀌었습니다. 기존 파일 일부만 덮지 말고 ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요. 공유 메모리 프로토콜은 v4 그대로입니다.
- 이미 저장된 로딩 통계(`SkyrimDiag_LoadStats.json`)에 들어 있는 게임 시작 시간은 새 로딩 기록이 쌓이면서 밀려납니다. 바로 낮추려면 그 파일을 지워도 됩니다.
- 고치지 않은 것: 처리된 치명적 예외를 Helper가 확인하는 약 11초 사이에 난 진짜 CTD는 여전히 기록되지 않고, 그 뒤 게임이 꺼지면 앞의 예외가 크래시로 남습니다(리뷰 #2, ADR-0017). 확인하는 동안 기록을 다시 여는 방법을 만들었지만, 출시 전 검수에서 진짜 크래시의 리포트를 잃거나 부수 예외가 크래시로 잡히는 경우가 나와 이번에는 넣지 않았습니다. Wine/Proton에서 뷰어 대신 실행하는 분석기를 5분 뒤에도 끝내지 않는 동작(끝까지 둬야 리포트가 완성됨), 1.6.1170 `SkyrimSE.exe+01949D3`의 시그니처(Ghidra로 보니 775곳에서 부르는 엔진 공용 잠금 함수라, Engine Fixes 미설치로 단정할 근거가 없음).
