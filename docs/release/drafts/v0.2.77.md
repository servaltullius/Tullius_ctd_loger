# v0.2.77 — 모드 DLL 크래시를 Crash Logger가 있어도 같은 답으로, 포인터 자리의 FormID에 폼 이름, 스크립트 로더 크래시에서 엉뚱한 모드를 짚지 않기

v0.2.77-rc1과 rc2를 묶어 정식으로 내는 릴리즈입니다. rc2 이후에는 배포되는 파일의 코드가 바뀌지 않았습니다(문서만, 아래 "rc2 이후 바뀐 것"). v0.2.76에서 올리면 Helper와 분석기가 바뀌고, 플러그인과 뷰어의 코드, 설정은 v0.2.76과 같습니다(SharedLayout protocol v4 그대로, 새 설정 없음). ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

v0.2.76 이전 버전이 분석해 둔 덤프는 뷰어에서 열 때 한 번 다시 분석합니다. rc1이나 rc2로 분석해 둔 덤프는 버전 번호(0.2.77)가 같아서 자동으로 다시 분석하지 않습니다. 새 문구를 보려면 뷰어에서 덤프를 고른 뒤 "지금 분석"을 눌러 주세요.

## 한눈에 보기
- **모드 DLL 안에서 튕긴 크래시가 Crash Logger를 쓸 때 오히려 약하게 나오던 문제를 고쳤습니다.** 모드 DLL 안에서 튕겼고 콜스택도 그 DLL을 가리키는 크래시는, Crash Logger 로그가 없으면 "가능성 중간", 있으면 "가능성 낮음"으로 나왔습니다. 권장 동반 모드인 Crash Logger를 쓰는 사람이 더 약한 답을 받은 셈입니다.
  - 이제 둘 다 "가능성 중간"입니다. Crash Logger의 프레임은 예외가 난 위치를 한 번 더 말할 뿐이라 가능성을 높이지도 낮추지도 않습니다. 같은 위치를 두 번 세지 않으므로 "가능성 높음"으로 올리지는 않습니다.
  - 리포트 전체가 같은 설명을 합니다. 결론 문장, 빠른 답, 근거 목록, 권장 사항이 모두 "Crash Logger 프레임과 스택이 모두 이 DLL을 가리키지만, 둘 다 예외가 난 위치를 보는 것"이라고 적습니다. "이 단서가 계속 고립되어 있으면 재수집하라"는 권장은 가능성이 낮을 때(Crash Logger 프레임만 있거나 스택 근거가 약할 때)만 남습니다.
  - 빠른 답의 "다른 모드가 일으킨 문제가 여기서 드러나는 경우도 있습니다" 문장은 그대로입니다. 모드 DLL 안에서 튕겼다는 것만으로 그 모드를 원인으로 단정하지 않습니다.
- **폼의 번호(FormID)를 포인터처럼 쓰다가 튕긴 크래시에서, 어느 폼이었는지 리포트에 나옵니다.** 모드가 폼을 가리키는 포인터 자리에 FormID를 넣어 쓰면, 크래시 레지스터에는 `0x12EB6` 같은 작은 값이 남습니다. 지금까지는 "이미 해제된 메모리나 망가진 포인터"라고만 했습니다.
  - Helper가 크래시 순간 레지스터 값을 게임의 FormID 표에서 찾아, 찾은 폼을 덤프에 넣습니다. 분석기는 그 폼의 종류, 이름, 플러그인을 붙입니다.
  - 리포트 예: `예외 명령어: movzx byte ptr [rax+0x1a] (0F B6 58 1A), read 0x12ED0, rax=0x12EB6 -> bad_pointer (rax 값은 이 폼의 FormID: TESObjectARMO "[U] 견고한 철 방패" (FormID 0x00012EB6, Skyrim.esm -> MUNG_UBE Armor Patch 2.esp))`
  - 빠른 답의 "어떻게 튕겼나": "폼의 번호(FormID)를 포인터처럼 쓰다가 튕긴 것으로 보입니다."
  - 2026-11-15와 11-16에 같은 세이브를 불러오다 난 크래시 두 건(OSLAroused.dll, 레지스터 값 `0x12EB6` = 철 방패)이 계기였습니다. 그 두 덤프는 이 기능 이전의 Helper로 찍어서 다시 분석해도 폼 이름이 나오지 않습니다.
- **Papyrus 스크립트를 읽다 튕긴 크래시에서 엉뚱한 모드를 짚지 않습니다.** 2026-11-17 메인 메뉴 로딩 중 크래시에서 v0.2.77-rc1 리포트는 "의심되는 모드: Animation Queue Fix — 가능성 낮음"이라고 했습니다. 실제 원인은 4096바이트가 넘는 설명 문자열이 든 스크립트(.pex)였습니다.
  - 크래시 스레드의 콜스택이 스레드 시작점까지 전부 게임과 Windows 코드뿐이면, 스택 메모리에 남은 예전 값을 훑어 모드를 찾는 "스택 스캔"을 하지 않습니다. 그 크래시의 Animation Queue Fix는 그렇게 남은 값이었고, 같은 크래시가 두 번 나자 "반복 이력"까지 더해졌습니다.
  - 크래시 근처에 Papyrus 스크립트 로더가 있으면 알아봅니다. 빠른 답: "게임이 튕겼습니다(CTD). Papyrus 스크립트(.pex)를 읽는 중이었던 것으로 보입니다. 원인 모드는 특정하지 못했습니다." 해볼 일: "최근에 추가하거나 업데이트한 모드와 새로 컴파일한 스크립트(.pex)부터 하나씩 끄거나 이전 파일로 되돌려 보세요."
  - 포인터 자리를 글자가 덮어썼으면 그 글자를 보여 줍니다. 그 크래시에서는 `rax=0x2065726120736C6C`가 글자 "lls are "였고, 이 글로 모드 폴더를 검색하면 문제 스크립트가 바로 나왔습니다. 리포트: `(rax 값은 글자 "lls are ")`, 빠른 답: "포인터 자리를 글("lls are ")이 덮어썼고, 그 값을 주소로 쓰다가 튕겼습니다(메모리 손상)."

## rc2 이후 바뀐 것
- 배포되는 파일의 코드는 rc2와 같습니다.
- rc2 노트와 ADR-0033·0034에 rc2 공개 패키지로 게임에서 확인한 결과를 더했습니다(아래 "실게임에서 확인한 것").

## 엔진 변경
**Helper**
- 크래시 덤프를 쓸 때 레지스터 값 중 0x10000 이상 0xFFFFFFFF 이하인 것을 게임의 FormID 표(`TESForm::allForms`)에서 찾고, 찾으면 표에서 읽은 부분과 그 폼을 덤프에 넣습니다(ADR-0033). 표 위치는 Address Library로 구합니다(SE ID 514351, AE ID 400507). 게임에 붙을 때 한 번 구해 `SkyrimDiagHelper.log`에 `FormID lookup for crash dumps: TESForm::allForms at the game executable+0x…`로 남깁니다. 표가 이상하면(크기, 연결, 폼의 FormID가 다름) 아무것도 넣지 않습니다. 찾은 조회가 있으면 크래시 덤프가 그만큼(조회마다 수백 바이트) 커집니다.
- Address Library 파서를 Helper와 분석기가 함께 쓰도록 옮겼습니다(동작은 그대로).

**분석기**
- 예외가 난 DLL의 후보를 정하는 후처리가 신뢰도 규칙을 따로 갖지 않습니다. 그 후보 자신의 신호에서 Crash Logger 프레임만 빼고 후보 합의를 다시 돌려 그 결과를 씁니다. Crash Logger 프레임밖에 없었으면 "낮음" 참고 단서입니다. 다른 후보(같은 Crash Logger 로그의 오브젝트 참조 등)는 넣지 않아, Crash Logger 없이 분석했을 때 없는 "신호가 갈림"이 생기지 않습니다.
- 스택만으로 "중간"이 되는 스택 가중치(5)를 한 곳에 두고 후보 합의와 독립 콜스택 판정이 함께 읽습니다. 값은 그대로입니다.
- 결론 문장의 "Crash Logger 프레임과 같은 덤프의 스택이 모두 이 DLL을 가리킨다" 분기가 조건 때문에 한 번도 나올 수 없었던 것을 고쳤습니다. 결론 문장과 권장 사항이 같은 Crash Logger 프레임 설명 함수를 씁니다.
- 덤프에서 명령 바이트를 읽을 때 요청의 앞부분만 덤프에 있으면 나머지를 로컬 모듈 파일로 채웁니다. 덤프에 아예 없는 주소를 로컬 파일에서 읽던 규칙과 같습니다. 게임 코드(SkyrimSE.exe)는 지금처럼 덤프에서만 읽습니다.
- FormID: Helper가 넣은 폼을 덤프에서 다시 찾아 예외 명령어 설명, 빠른 답의 "어떻게 튕겼나", 리포트 줄, 요약 JSON(`fault_instruction.base_value_form`)에 붙입니다. 어느 모드가 원인인지, 후보, 버킷 키는 바꾸지 않습니다.
- 크래시 스레드의 콜스택이 스레드 시작점까지 풀렸고 모드 프레임이 없으면(스레드 시작 지점을 감싸는 훅만 있는 경우 포함) 스택 스캔을 하지 않습니다(ADR-0034). 프리징은 지금처럼 스캔합니다. 오버레이 같은 외부 프로그램의 DLL이 경로에 있으면 스캔합니다.
- 스택 스캔만으로 생긴 후보는 빠른 답에서 "튕긴 곳은 다른 파일이고 단서가 이 모드를 가리키지만" 대신 "이 모드는 게임이 튕길 때 메모리 근처에서 보였을 뿐이라 약한 단서입니다"라고 말합니다. 그 후보가 예외가 난 모듈 자체이면 "이 모드 안에서 튕겼지만"을 그대로 씁니다. 후보와 가능성 낮음은 그대로입니다.
- 주소가 될 수 없는 값으로 튕겼고 그 레지스터 값이 글자(출력 가능한 ASCII 8자, 또는 UTF-16 4자)이면 그 글자를 근거 문장, 빠른 답, 리포트 줄, 요약 JSON(`fault_instruction.overwritten_text`, `overwritten_text_register`)에 적습니다. 글자는 메모리에 있는 그대로라 그대로 검색할 수 있습니다.
- 새 시그니처 `PAPYRUS_SCRIPT_LOAD`(크래시 메커니즘, 신뢰도 중간): 게임 본체(SkyrimSE.exe)의 접근 위반이고 크래시 근처에 `BSScript::CompiledScriptLoader`가 있을 때. 0 근처 주소를 읽은 널 포인터 크래시는 지금처럼 널 포인터 시그니처가 먼저입니다.
- 모드를 특정하지 못한 크래시에서는, 자기 제목이 있는 메커니즘 시그니처(지금은 `PAPYRUS_SCRIPT_LOAD`뿐)가 빠른 답의 제목, 해볼 일, 확실하지 않은 이유를 채웁니다. 크래시 직전에 그래픽 드라이버 오류가 있으면 드라이버 쪽이 먼저입니다.
- 새 권장 사항 태그 `[알려진 크래시 메커니즘]`. 다음 조치 순서에서 모드 단위 줄(행동 우선 후보, Crash Logger 프레임, 오브젝트 참조) 뒤, "같은 파일을 여러 모드가 제공" `[충돌]` 줄 앞입니다.

**크래시 테스터(개발용, 배포 ZIP에 없음)**
- Ctrl+Shift+Home: FormID `0x00012EB6`을 폼 포인터로 써서 폼 종류를 읽는 크래시(`AutoScenario=14`). 시작 로그 줄에 Home이 나옵니다.

**CI·테스트(내부)**
- 같은 모드 DLL 크래시를 Crash Logger 프레임이 있을 때와 없을 때로 만들어, 후보·빠른 답·결론·근거·권장이 같은지 확인하는 테스트. 약한 스택, 프레임만 있는 경우, 다른 플러그인의 오브젝트 참조가 있는 경우도 확인합니다.
- 덤프 부분 읽기를 로컬 파일로 채우는 테스트(`skydiag_stackwalk_e2e_tests`).
- 빈 함수 포인터 크래시 테스트가 덤프 폴더를 지울 때 예외를 던지지 않습니다(백신이 파일을 잡고 있어도 통과한 테스트가 실패하지 않음).
- FormID 표 조회 테스트(`skydiag_form_map_tests`), Helper 수집부터 실제 미니덤프와 분석기까지의 e2e(`skydiag_crash_object_e2e_tests`), 레지스터 글자·스택 스캔 판정·스크립트 로더 시그니처·빠른 답·다음 조치 순서 테스트.
- ADR-0033, ADR-0034.

## 실게임에서 확인한 것
모두 같은 MO2 환경(게임 1.6.1170, Crash Logger 1.27 켬, 켜진 모드 약 4,380개)에서 한 것입니다.
- **이 릴리즈와 같은 코드의 빌드**(v0.2.77-rc2 공개 패키지, 2026-11-17):
  - 크래시 테스터 Ctrl+Shift+Home: 위 "한눈에 보기"의 리포트 줄과 빠른 답이 그대로 나왔고, 요약 JSON의 `fault_instruction.base_value_form`에도 같은 폼이 들어갔습니다. 빠른 답은 "CrashTester (dev test) — 가능성 중간"이었고, 결론 문장은 Crash Logger 프레임과 스택이 모두 그 DLL을 가리키지만 둘 다 예외가 난 위치를 보는 것이라고 적었습니다. 플러그인의 알림으로 하트비트 확인 없이 곧바로 크래시로 확정했고, 덤프(72.7MB), 리포트, 같은 크래시의 Crash Logger 로그, 종료 뒤 뷰어가 남았으며 종료 코드는 1이었습니다.
  - 세이브를 불러온 뒤 크래시 없이 끝난 세션: Helper 로그의 `FormID lookup for crash dumps: TESForm::allForms at the game executable+0x20FBB88.`, 호환성 사전 점검 경고·오류 0건, 종료 코드 0, 기록 없음.
- **FormID 기능의 로컬 빌드**(2026-11-17 02:47): 크래시 테스터 Ctrl+Shift+Home에서 위와 같은 리포트 줄과 빠른 답이 나왔습니다. 폼의 플러그인(Skyrim.esm → MUNG_UBE Armor Patch 2.esp)은 그 레코드를 마지막으로 덮어쓴 플러그인과 같습니다. 같은 빌드로 빈 함수 포인터 호출(Ctrl+Shift+End)의 결과가 이전과 같은 것도 확인했습니다.
- **v0.2.77-rc1과 같은 코드의 빌드**(2026-11-16 19:50): 세이브를 불러오다 OSLAroused.dll 안에서 난 실제 크래시(`cmp byte ptr [rdx+0x1a]`, `rdx=0x12EB6`)에서 빠른 답이 "OSL Aroused - Arousal Reborn — 가능성 중간"이었고, 결론 문장이 Crash Logger 프레임과 스택이 모두 그 DLL을 가리키지만 독립 검증은 아니라고 적었습니다. 같은 크래시의 Crash Logger 로그와 짝지어졌고, 알림으로 곧바로 확정, 종료 코드 1, 종료 뒤 뷰어. 이 크래시가 FormID 기능의 계기입니다.
- 스크립트 로더 크래시: 실제 게임에서 난 2026-11-17의 두 크래시 덤프를 이 릴리즈의 분석기로 다시 분석해 위 빠른 답과 리포트 줄을 확인했습니다. 그 스크립트를 고친 뒤에는 같은 크래시가 나지 않았습니다.
- 실게임 미확인:
  - 이 릴리즈의 Helper로 찍은 덤프에서의 글자 덮어쓰기 문장과 스크립트 로더 빠른 답. 그런 크래시가 다시 나지 않아, 그 전에 찍은 덤프의 재분석으로만 확인했습니다.
  - 찾은 폼을 크래시 오브젝트보다 먼저 덤프에 넣는 순서. 덤프에 넣는 크래시 오브젝트 메모리가 상한까지 찬 경우에만 결과가 달라지는데, 그런 상황을 만들지 않았습니다.
  - SE 1.5.97과 1.7.x 게임.
  - 크래시를 잡아 덤프를 쓰는 흐름은 v0.2.76과 같으므로, v0.2.76 노트의 실게임 미확인 목록이 그대로 해당합니다.

## 주의사항
- 예외 위치가 모드 DLL이어도, Crash Logger의 오브젝트 참조나 다른 독립 근거가 함께 맞아야 "가능성 높음"이 됩니다. 이 릴리즈는 Crash Logger를 쓸 때와 안 쓸 때의 차이를 없앤 것이고, 그 기준은 바꾸지 않았습니다.
- FormID 이름은 이 버전의 Helper로 찍은 크래시 덤프에서만 나옵니다. 그 전 덤프는 다시 분석해도 나오지 않습니다.
- 0x10000 미만의 FormID(플레이어 0x14 같은 Skyrim.esm 앞쪽 폼)는 일부러 찾지 않습니다. 그 구간의 값은 대개 개수나 인덱스라 우연히 맞기 쉽기 때문입니다.
- SE 1.5.97과 1.7.x에서는 FormID 조회와 스크립트 로더 판정을 돌려 보지 않았습니다.
- 모드가 데이터를 망가뜨리고 빠져나간 뒤 게임 코드에서 튕긴 크래시는, 이제 스택 스캔 후보 없이 "원인 모드는 특정하지 못했습니다"가 될 수 있습니다. 스택에 남은 예전 값만으로 모드를 짚던 것을 멈춘 결과입니다.
- 글자 판정은 ASCII와 UTF-16의 ASCII 범위만 봅니다. UTF-8 한글처럼 여러 바이트 글자가 8바이트 경계에 걸친 값, 탭·줄바꿈이 섞인 값은 알아보지 못합니다.
