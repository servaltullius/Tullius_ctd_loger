# v0.2.61 — 덤프에서 원인 오브젝트 읽기와 프리징 원인 스레드 찾기

v0.2.61-rc1부터 rc3까지의 변경과, 원인을 미리 아는 사고로 한 실게임 크래시 테스트에서 찾아 고친 것을 묶은 정식 릴리즈입니다. 기존 파일 일부만 덮지 말고 ZIP 전체를 설치해 주세요.

## 핵심 변경
- **크래시 당시 오브젝트를 덤프에서 직접 읽기** — 크래시 레지스터와 스택이 가리킨 게임 오브젝트의 타입, FormID, 이름, 정의·수정한 플러그인, 레퍼런스의 기반 오브젝트를 Crash Logger 로그 없이도 보여 줍니다. 예: `RCX: Character "리디아" [0x000A2C94] Update.esm -> SkyrimHouseRemodel.esp (base TESNPC [0x000A2C8E] Skyrim.esm -> TKL - NPC Face Fixer.esp)`. 아직 후보 선정에는 쓰지 않습니다.
- **프리징 때 메인 스레드가 기다린 게임 스레드 찾기** — 1.6.1170에서 창·렌더를 맡는 첫 스레드는 매 프레임 게임 작업 스레드(SKSE task가 도는 곳)를 엔진 안에서 기다립니다. 플러그인 task가 멈춘 프리징을 이전에는 "엔진 안에서 대기"라고만 했지만, 이제 그 시각 플러그인 코드 안에 있던 게임 작업 스레드를 찾아 그 플러그인을 후보와 다음 조치로 올립니다.
- **Windows 업데이트 뒤에도 덤프 분석** — 덤프에 시스템 DLL과 그래픽 드라이버의 스택 해제 정보와 함수 이름표를 담아(약 17MB), 업데이트 뒤나 다른 PC에서 다시 열어도 스택을 풀고 이름을 붙입니다.
- **캡처 당시 메모리** — 리포트의 `메모리:` 줄(사용 가능 RAM, 시스템 커밋, 게임 커밋, 워킹셋)과 `GPU:` 줄(게임의 VRAM 사용량과 예산, Crash Logger의 `GPU MEMORY`와 같은 값). 커밋이나 VRAM이 한도의 90% 이상이면 `[메모리]` 권장 조치가 붙습니다. 모드를 지목하지는 않습니다.
- **Crash Logger 연동 보강** — 원래 예외(예: assert의 `EXCEPTION_BREAKPOINT`), 플러그인이 없는 관련 오브젝트, C++ 예외 정보를 읽고, 플레이어가 서 있던 셀을 후보로 올리지 않으며, 상위 모듈을 콜스택 순서로 정렬합니다. Crash Logger가 처리되지 않은 예외로 기록한 C++ 예외는 "잡힌 예외일 수 있음"이 아니라 실제 CTD로 설명합니다.
- **문제 모듈 경고** — SkyrimCrashGuard처럼 크래시를 가로채 게임을 계속 돌리는 모듈이 로드되어 있으면 `[문제 모듈]`로 알려 줍니다(Crash Logger의 문제 모듈 목록과 같음).
- **같은 원인의 프리징을 한 묶음으로** — 메인 스레드의 대기와, 찾았다면 그 대기를 붙잡은 플러그인으로 프리징 버킷(`HANG1-`)을 정합니다.
- **리포트 정리** — 리포트는 블랙박스 이벤트 개요와 최근 60개만(146\~193KB → 약 11\~17KB), 요약 JSON은 플러그인 개수만(1.6MB → 약 12\~23KB) 담습니다. 상황에 맞지 않는 권장 조치, SKSE 런타임 같은 잡음 후보, 한국어 리포트의 영어 용어를 정리했고, MO2 모드 이름에서 Nexus 압축 파일 이름의 꼬리(`SmoothCam 41252 1.8.1 2026` → `SmoothCam`)를 떼어 냅니다.

## 엔진 변경
- Helper: CTD 순간 크래시 레지스터와 스택 위쪽이 가리킨 오브젝트(MSVC RTTI, 최대 2MB), 모든 덤프에 Windows 폴더 모듈의 PE 헤더·export·`.pdata`·UNWIND_INFO(최대 24MB)와 게임의 그래픽 어댑터별 VRAM 사용량·예산(사용자 스트림 `0x1474D`)을 담습니다.
- 분석기: 덤프 오브젝트(ADR-0010), 덤프 안의 스택 해제 정보(ADR-0011), 메모리(ADR-0012), 문제 모듈(ADR-0013), 막힌 게임 스레드(ADR-0009 보강)를 근거 항목, 리포트, 요약 JSON(`dump_objects`, `memory`, `problematic_modules`, `freeze_analysis.main_thread_wait.blocked_thread`, `crash_logger.exception`, `crash_logger.objects_without_plugin`)에 넣습니다.
- 분석기: SKSE 런타임(`skse64_*.dll`)은 그 안에서 직접 크래시가 난 경우가 아니면 스택 후보와 "근처 DLL 비교" 안내에서 뺍니다.
- WinUI: `[문제 모듈]`을 "지금 할 일"에 넣습니다.
- 개발: Windows CI가 컴파일 결과를 캐시하고(릴리즈 빌드는 제외), PR에서는 바뀐 파일만 clang-tidy로 검사합니다. 원인을 아는 사고를 실게임에서 일으키는 개발용 SKSE 플러그인 `tools/crash_tester`를 추가했습니다(배포하지 않음).

## 실게임에서 확인한 것
- 한 사용자의 MO2 환경(게임 1.6.1170, SKSE 2.2.6, 플러그인 약 4,250개, Crash Logger 1.25)에서 확인했습니다.
- rc1·rc3 수동 캡처: 덤프 약 599MB(시스템 DLL 정보로 약 17.7MB 증가), 리포트 약 11KB, 요약 JSON 약 12~13KB, `메모리:`·`GPU:` 줄(RTX 4090, VRAM 예산 22.82GB = Crash Logger의 `GPU MEMORY` 예산), 정상 종료.
- 크래시 테스트(2026-10-12): `tools/crash_tester`로 원인을 아는 사고 7건(프리징 3, CTD 4)을 무인으로 일으켰습니다.
  - 접근 위반 CTD: 후보와 다음 조치가 원인 DLL, 덤프 오브젝트에 NPC 이름·기반 NPC·플러그인(Crash Logger의 오브젝트 참조와 일치).
  - 브레이크포인트 CTD: `0x80000003`과 "모드가 스스로 멈춘 것" 해석.
  - C++ 예외 CTD: Crash Logger의 예외 타입·메시지·throw 위치 연동, 실제 CTD로 설명(수정 후).
  - 게임 EXE 안의 접근 위반(`SkyrimSE.exe+0xcc90cf`): 콜스택으로 원인 DLL을 찾아 유일한 후보로.
  - 프리징 3건: 처음에는 원인을 못 찾았고, 고친 뒤 3건 모두 원인 DLL을 지목. 같은 원인 2건은 같은 버킷, 다른 원인 1건은 다른 버킷.
  - `[문제 모듈]` 경고(SkyrimCrashGuard 이름의 빈 DLL), 메모리 기록.
- 보관 덤프 재분석으로만 확인: Crash Logger 원래 예외·플러그인 없는 오브젝트·셀 제외·상위 모듈 순서(실사고 CTD 4건), MO2 모드 이름 정리(실제 폴더 4,729개 중 15개만 바뀜).
- 실게임 미확인: 막힌 게임 스레드 판정이 실제 프리징에서 오탐을 내지 않는지(보관 중인 실사고 프리징에는 해당 모양이 없음), Windows 업데이트 뒤 새 덤프 분석, PSS 스냅샷 덤프의 커밋 표시, 실제 SkyrimCrashGuard, AMX CPU의 CTD 덤프(CI에서만 확인).

## 주의사항
- 플러그인 코드와 공유 메모리 프로토콜(SharedLayout v4)은 v0.2.60과 같지만 Helper, 분석기, WinUI가 바뀌었고 버전 정보도 바뀌었습니다. ZIP 전체를 교체해 주세요.
- 덤프가 약 17MB 커집니다. 덤프 오브젝트, 시스템 DLL 정보, VRAM은 이 버전으로 새로 찍는 덤프부터 들어갑니다. 이전 덤프의 RAM·커밋은 다시 분석하면 보입니다.
- 막힌 게임 스레드는 "그 시각 플러그인 코드 안에 있던 게임 스레드"로 추정합니다. 메인 스레드가 정확히 어느 스레드를 기다렸는지는 덤프로 알 수 없습니다.
- 레벨드 리스트에서 생긴 액터(대부분의 적)는 기반이 실행 중에 만든 임시 NPC라 이름만 나오고 플러그인은 나오지 않습니다.
- 문제 모듈은 파일 이름이 정확히 같을 때만 찾습니다. 이름이 바뀌는 모드는 이력의 후보 키가 한 번 바뀌고, 새 프리징 버킷 키는 이전 이력의 키와 합쳐지지 않습니다.
- 검수된 실사고 코퍼스가 없어 다른 크래시 로거 대비 적중률을 수치로 주장하지 않습니다.
