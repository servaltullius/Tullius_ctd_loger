# v0.2.76-rc1 — 처리된 예외가 반복될 때의 끊김 제거, 게임 함수의 Address Library ID, 크래시 직전 드라이버 오류, 끄는 중 프리징 오판 정리

v0.2.75 이후의 수정을 모은 테스트용 프리릴리즈입니다. 게임이 주기적으로 끊긴다는 넥서스 제보 가운데 원인이 확인된 한 건의 수정이 들어 있습니다. 그 수정은 제보 환경에서 아직 확인되지 않았습니다. 플러그인, Helper, 분석기, 뷰어가 모두 바뀌었으니 ZIP 전체를 설치해 주세요(SharedLayout protocol v4는 그대로). MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요. 새 설정은 `SkyrimDiagHelper.ini`의 `MaxForcedCloseCrashDumps`(기본 3)와 `KeepSlowShutdownHangDumps`(기본 0)입니다.

## 한눈에 보기
- **게임이 스스로 처리하는 예외가 반복돼도 그때마다 멈추지 않습니다**(ADR-0031). 기본 설정(`CrashHookMode=1`)에서 Helper는 접근 위반 같은 예외가 나면 게임이 그것을 처리하는지 알기 전에 덤프부터 썼고, 덤프를 쓰는 동안에는 게임의 모든 스레드가 멈춥니다. 어떤 모드나 엔진 코드가 같은 예외를 내고 스스로 처리하기를 반복하는 구성에서는 그때마다 1초쯤 끊겼습니다(넥서스 제보의 측정: v0.2.73에서 메인 스레드 정지 1,162ms). 이제 같은 예외(코드와 주소)가 한 게임 세션에서 두 번 "처리됨"으로 끝나면, 세 번째부터는 덤프를 쓰기 전에 게임이 계속 도는지 먼저 확인하고, 계속 돌면 아무것도 쓰지 않습니다. 메인 스레드의 예외에도 적용하고 세션이 끝날 때까지 기억합니다.
  - 제보 환경의 이전 버전 Helper 로그(2026-11-11)에는 같은 주소의 접근 위반이 23분 동안 14번(가장 짧은 간격 9초), 여섯 개의 서로 다른 스레드에서 나왔고 모두 게임이 처리했습니다. 그때마다 덤프를 썼습니다. 이 버전의 규칙으로는 그중 처음 두 번만 덤프를 씁니다.
  - 처음 두 번은 전처럼 덤프를 먼저 쓰므로 세션 초반의 끊김 두 번은 남습니다.
  - 회복하지 못하면 그때 덤프를 씁니다. 다만 이미 두 번 처리됐던 바로 그 주소에서 진짜 크래시가 나고 확인 도중 게임이 곧바로 꺼지면, 덤프 없이 예외 기록(`SkyrimDiag_PostExitCrashEvidence_*.json`)만 남습니다.
- **게임 함수 프레임에 Address Library ID가 붙습니다**(ADR-0027). 콜스택의 게임 프레임이 `SkyrimSE.exe+0x49fb54 (ID 29895+0xe4)`처럼 나옵니다. 내장 목록에 이름이 있는 함수는 `(TESConditionItem::IsTrue+0x6bc, ID 29924)`처럼 이름과 함께 나옵니다. Helper가 게임 버전에 맞는 Address Library 파일을 한 번 읽어 크래시·프리징·수동 덤프에 넣고, 분석기는 함수의 시작 주소가 ID의 주소와 정확히 같을 때만 붙입니다(가까운 ID로 추측하지 않음).
- **크래시 콜스택을 맨 위 프레임부터 보여 줍니다.** 지금까지는 첫 플러그인 프레임의 두 프레임 위에서 시작해서, 크래시 지점과 그 사이의 게임 함수가 잘렸습니다. 위쪽이 8프레임보다 길면 처음 4개와 `... 프레임 N개 생략` 줄로 줄입니다. 스택이 후킹 코드에서 끊기면 그렇다고 적고, 그 뒤에 기록된 점프가 어디로 가는지 알려 줍니다. 버킷, 알려진 크래시 판정, 의심 모드는 바뀌지 않습니다.
- **크래시 직전에 그래픽 드라이버 오류가 있었으면 그것부터 확인하라고 안내합니다**(ADR-0029). 11/10의 게임 시작 중 크래시는 `nvlddmkm` 153(드라이버 재시작) 14초 뒤였고, 덤프로 보면 장치가 사라져 텍스처 생성이 실패한 것이었는데 리포트는 크래시가 난 모드를 끄거나 업데이트하라고 했습니다. 이제 Helper가 크래시 덤프 옆에 `<덤프 이름>_GpuDriverEvents.json`을 쓰고, 분석기는 크래시 60초 안의 드라이버 오류를 빠른 답과 `[크래시 직전 드라이버 오류]` 줄로 먼저 안내합니다. 의심 모드는 두 번째로 확인할 것으로 남기고, 시간이 가깝다는 것만으로 원인은 아니라고 적습니다.
- **게임을 강제로 끄다 난 오류의 덤프가 진짜 크래시 덤프를 밀어내지 않습니다.** 이런 덤프(ADR-0022: 뷰어를 열지 않고 기록에도 넣지 않음)가 `MaxCrashDumps` 자리를 진짜 크래시와 똑같이 차지해서, 11/09 밤의 18건이 그날 크래시 9건의 덤프와 리포트를 지웠습니다. 이제 새 설정 `MaxForcedCloseCrashDumps`(기본 3, 0은 무제한)로 따로 셉니다.
- **끄는 중인 게임을 프리징으로 기록하지 않습니다.**
  - 게임이 이미 종료 절차에 들어가 스레드가 하나만 남았으면 프리징 덤프를 쓰지 않고, Helper 로그에 `Hang detected while the game is closing`만 남깁니다.
  - 메뉴에서 잡힌 프리징이 풀리지 않은 채 게임이 정상 종료(종료 코드 0)하면 느린 종료로 보고, 분석하기 전에 덤프와 딸린 파일을 지웁니다. 프리징 기록에도 남지 않습니다. 남기려면 `KeepSlowShutdownHangDumps=1`로 두세요. 플레이 중 프리징은 전처럼 바로 분석하고 지우지 않습니다. 게임의 대화 상자(오류 창)가 떠 있던 캡처도 지우지 않습니다.
- **수동 캡처 때 게임이 멈춰 있었으면 프리징으로 분석합니다**(ADR-0028). 하트비트가 5초 넘게 멈춰 있고 게임 창이 앞에 있었거나 응답하지 않았으면 프리징으로 봅니다. 지금까지는 수동 캡처면 "프리징 아님, 할 일 없음"이라고 답했습니다. 뒤에 있지만 창이 응답하는 게임(일시정지일 수 있음)은 전처럼 스냅샷입니다.
- **.NET 런타임을 의심 모드로 지목하지 않습니다.** 프리징 리포트가 "의심 모드: clr.dll"이라고 답한 사례가 있었습니다. `clr.dll`은 .NET 코드를 쓰는 모드나 오버레이가 게임에 올리는 Windows 구성 요소입니다. .NET을 올리는 모드 자체(예: NetScriptFramework)는 계속 모드로 봅니다.
- **Helper가 뜨자마자 계속 꺼지는 환경에서 플러그인이 다시 띄우기를 그만둡니다**(ADR-0030). 지금까지는 Helper가 몇 초 만에 꺼지는 일이 반복되면(보안 프로그램이 끄거나 시작 중 오류) 게임이 도는 내내 같은 간격으로 다시 띄웠습니다. 이제 실패한 시작 뒤에는 1·2·4·8초를 기다리고, 다섯 번 연속 실패하면 그 세션에서는 더 띄우지 않으며 `SkyrimDiag.log`에 한 번 적습니다. 1분 넘게 돌다가 사라진 Helper는 전처럼 바로 다시 띄웁니다.

## 수정
**Helper**
- 반복되는 처리된 예외(ADR-0031): 확인 중 게임이 회복하면 캡처 상태를 풀고 `No dump written: this repeated exception was handled again and the game kept running`을 로그에 남깁니다. 그 뒤 60초 안에 게임이 비정상 종료하면 `SkyrimDiag_PostExitCrashEvidence_*.json`에 기록합니다. "10분 안에 두 번이면 최소 덤프"와 그 뒤의 다시 쓰기는 없앴습니다(최소 덤프도 쓰는 동안 게임을 멈춥니다). C++ 예외(`0xE06D7363`)와 중단점(`0x80000003`)은 대상이 아닙니다.
- 풀어 준 크래시 덤프(ADR-0028): 처리된 것으로 보고 풀어 준 덤프는 더 새 크래시의 덤프가 쓰인 뒤에만 지웁니다. 그 쓰기가 실패하고 게임이 1분 안에 비정상 종료하면 풀어 준 덤프를 그 크래시의 덤프로 보고합니다. 종료 때 이렇게 올린 덤프에도 플러그인 스캔과 인시던트 매니페스트를 붙이고, 종료 뷰어가 열리지 않으면 분석을 시작합니다. 1분 넘게 지난 덤프 쓰기 실패는 그 종료의 크래시로 보고하지 않습니다.
- 프리징 에피소드는 하트비트가 다시 움직여야 끝납니다. 로딩 표시로 임계값만 올라간 경우를 "회복"으로 풀던 문제입니다.
- 느린 종료 판정: 종료 코드 0, 메뉴에서 잡힌 캡처, 종료 시점에도 멈춰 있는 하트비트가 모두 맞아야 합니다. 회복한 직후 빠르게 끈 경우는 덤프를 남기고 분석합니다. 캡처 뒤 게임이 종료 절차에 들어간 것을 봤으면 어디서 잡혔든 프리징 뷰어를 열지 않습니다(덤프는 남김).
- 프리징 덤프 쓰기가 실패하면 그 캡처의 WCT 파일을 지우고, 게임이 닫는 중이었는지 다시 확인합니다.
- 프리징·수동 캡처의 WCT에 게임 창이 앞에 있었는지(`capture.gameInForeground`)와 응답했는지(`capture.gameWindowResponsive`)를 적습니다.
- Address Library 파일을 덤프의 새 스트림으로 넣고, 로그에 `Address Library for dumps: N bytes.`를 남깁니다. 파일이 없으면 전처럼 ID 없이 동작합니다.
- 크래시 덤프가 확정된 뒤 시스템 로그의 그래픽 드라이버 기록을 덤프 옆 파일로 씁니다(읽기 한도 1.5초, 덤프 쓰기는 늦추지 않음).
- 강제 종료 중 오류의 인시던트 매니페스트에 `"forced_close": true`를 적습니다.
- 크래시 이벤트가 대기 중인 프리징 뷰어를 취소하는 것은 그 크래시가 남을 때만입니다. 로그 회전은 잠긴 로그가 있어도 보관본을 건드리지 않습니다.

**분석기**
- Address Library: 형식 1, 2, 5를 읽습니다. 요약 JSON `symbolization.address_library_ids`, 스택이 끊긴 곳의 `stackwalk_truncation.hook_page`·`hook_next_jump`·`hook_next_jump_distance`.
- 콜스택 표시: 리포트의 콜스택과 요약 JSON `callstack.frames`(뷰어가 보여 주는 것)가 프레임 0부터의 목록을 씁니다. 버킷 키와 알려진 크래시 판정은 전과 같은 범위를 읽습니다.
- 크래시 직전 드라이버 오류: 빠른 답의 할 일과 "확실하지 않은 이유", 권장 줄, 다음 조치에 반영합니다. 강제 종료 중 오류에는 적용하지 않고, 알려진 원인·설치 중이던 후킹·세이브 손상 의심은 여전히 앞섭니다. 60초보다 오래된 오류는 근거로만 남습니다.
- .NET: `\Windows\Microsoft.NET\` 아래 모듈, .NET Framework 네이티브 이미지(`*.ni.dll`), 공용 .NET 런타임 폴더, `clr.dll`·`clrjit.dll`·`coreclr.dll`·`mscoree.dll`·`mscoreei.dll`·`hostfxr`·`hostpolicy`를 Windows 구성 요소로 봅니다.
- 전체 검수(ADR-0028)에서 고친 것:
  - 그래픽 드라이버 기록에 건수만 있고 남은 이벤트가 없으면 분석이 죽던 문제.
  - MO2 `mods` 폴더 판정: 상위 폴더 이름이 `mods`이면 모든 DLL에 같은 엉뚱한 모드 이름이 붙었습니다.
  - Address Library "파일을 찾을 수 없음" 오류 창이면 빠른 답과 권장 사항이 Address Library 설치부터 안내합니다.
  - 후킹 설치 중 경합에는 "크래시 모듈을 알 수 없으니 다시 캡처" 줄을 붙이지 않습니다.
  - 점수가 같은 후보는 이름순이 아니라 신호가 나온 순서를 따릅니다.
  - `cc*` 플러그인은 `.esm`/`.esl`일 때만 Creation Club 콘텐츠로 봅니다.
  - 한글 경로에서 오류 출력과 런처 로그가 잘리던 문제(UTF-8로 씀).
  - 그 밖에 명령어 해석(쓰기에서의 GP 오류, 작은 베이스 + 큰 인덱스), 엔진 잠금 순환 탐색의 상한, 덤프 끝의 export 이름 읽기 등.
- `crash_signatures.json`: 수정 모드가 이미 로드된 경우의 문장 셋이 할 일부터 시작합니다(빠른 답에 보이는 부분).

**뷰어**

## 테스트 시 확인할 점
- 주기적인 끊김을 겪던 분: `SkyrimDiag.ini`의 `CrashHookMode`를 0으로 바꿔 두었다면 1로 되돌리고 평소처럼 플레이해 주세요. 세션 초반 두 번 뒤로는 끊김이 없어야 합니다. `SkyrimDiagHelper.log`에 `checking whether the game recovers before writing a crash dump`와 `No dump written: this repeated exception was handled again`이 나오는지 봐 주시고, 그 로그를 보내 주시면 예외가 얼마나 자주 반복되는지 알 수 있습니다.
- 크래시가 나면 리포트 콜스택의 게임 프레임에 `(ID …)`가 붙는지, 덤프 옆에 `_GpuDriverEvents.json`이 생기는지 봐 주세요.
- 게임이 굳었을 때 수동 캡처(Ctrl+Shift+Backspace)를 하면 프리징으로 분석되는지 봐 주세요.
- 메뉴에서 평소처럼 종료했을 때 프리징 뷰어가 뜨지 않는지 봐 주세요.
