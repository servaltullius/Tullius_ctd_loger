# v0.2.68-rc2 — 1.6.1170 프리징의 메인 스레드 판단 수정

rc1 실게임 확인에서 찾은 문제 하나를 고친 테스트용 프리릴리즈입니다. 바뀐 것은 프리징 분석이 기준으로 삼는 메인 스레드를 찾는 방법뿐입니다.

## 한눈에 보기
- **1.6.1170 프리징에서 엉뚱한 스레드를 메인 스레드로 보던 문제를 고쳤습니다(rc1에서 생김).** rc1은 60초마다 남기는 하트비트 이벤트의 스레드를 메인 스레드로 썼습니다. 그런데 1.6.1170에서는 SKSE 작업(하트비트 작업 포함)이 게임의 작업 스레드에서 돌아, 그 스레드 번호가 매번 바뀝니다(rc1 수동 캡처: 43864, 39912, 41636, 25652). 그래서 실제 프리징에서 창을 가진 메인 스레드 대신 작업 스레드를 분석해, 메인 스레드 대기와 Modal 대화상자 판정이 틀어질 수 있었습니다.

## 수정
- 플러그인: 플러그인을 로드한 스레드(세션 시작 기록과 같은 메인 스레드)의 번호를 기억해 하트비트 이벤트에 담습니다.
- Helper·분석기: 메인 스레드는 세션 시작 기록의 스레드이거나 하트비트 이벤트에 담긴 번호입니다(`MainThreadIdFromEvent`). 이벤트를 기록한 스레드 자체는 쓰지 않고, 메뉴·히치·로딩 이벤트는 근거로 쓰지 않습니다. rc1의 하트비트 이벤트(번호가 담기지 않음)는 무시하므로, rc1로 찍은 덤프도 v0.2.67처럼 세션 시작 기록으로 판단합니다.

## 정정
- rc1 노트는 "메인 스레드를 가장 최근 하트비트, 세션 시작, 메인 스레드에서 기록되는 히치·메뉴·로딩 이벤트 순으로 찾는다"고 했습니다. 1.6.1170에서는 그 이벤트들이 메인 스레드에서 기록되지 않아 이 설명과 동작이 틀렸습니다(위 수정).

## 테스트 시 확인할 점
- rc1과 같이 평소처럼 플레이하고 `Ctrl+Shift+F12`로 수동 캡처를 해 주세요.
- 프리징이 나면(일부러 낼 필요는 없습니다) 리포트의 메인 스레드 대기 설명이 그 상황과 맞는지 봐 주세요.

## 주의사항
- 플러그인, Helper, 분석기가 바뀌었습니다. ZIP 전체를 설치하고, MO2에서 새 모드로 설치했다면 rc1 모드는 꺼 주세요.
- Crash Logger 1.25가 설치돼 있으면 `Ctrl+Shift+F12`가 Crash Logger의 스레드 덤프 단축키이기도 합니다. 그때 Crash Logger가 일으키는 탐침 예외 때문에, 그 스레드에서 1분 안에 잡혔던 C++ 예외가 크래시로 잠깐 기록됐다가 하트비트 확인 뒤 지워질 수 있습니다(rc1 실게임에서 한 번 관찰, 덤프를 쓰는 몇 초 동안 게임이 멈출 수 있음). 결과 리포트에는 남지 않습니다.
