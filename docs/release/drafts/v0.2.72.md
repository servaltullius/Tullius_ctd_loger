# v0.2.72 — 덤프 크기 약 10분의 1, 덤프 폴더 용량 상한

덤프 하나의 크기를 약 10분의 1로 줄이고, 덤프 폴더 전체 크기에 상한(기본 5GB)을 둔 릴리즈입니다. 전체 검수에서 찾은 문제 15건도 고쳤습니다. Helper, 분석기, 뷰어가 바뀌었으니 ZIP 전체를 설치해 주세요(SKSE 플러그인은 버전만 올림, SharedLayout protocol은 그대로 v4). MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

**업데이트 뒤 처음 게임을 켜면, 덤프 폴더가 5GB를 넘을 때 오래된 덤프가 리포트와 함께 지워집니다.** 남기고 싶은 덤프가 있으면 업데이트 전에 다른 폴더로 옮기거나, 새 `SkyrimDiagHelper.ini`에 `MaxTotalDumpGB=0`(무제한)을 넣어 주세요. 예전 ini를 그대로 써도 이 키가 없으면 5GB가 적용됩니다.

## 한눈에 보기
- **덤프가 약 10분의 1로 작아집니다.** 큰 모드팩에서 덤프 하나가 0.5\~0.9GB였고, 용량의 대부분은 로드된 모든 모듈(약 500개)의 코드와, 크래시 덤프에서는 모든 모듈의 리소스였습니다. 분석기가 덤프에서 읽는 코드는 모두 어떤 스레드의 실행 위치나 스택 값 근처입니다. 그래서 기본 설정(`DumpMode=1`)의 덤프는 이제 게임 EXE의 코드 전체와, 스레드 스택이 가리키는 다른 모듈의 코드만 담습니다. 실게임에서 수동 캡처가 58\~60MB(이전 약 570MB), 크래시가 67MB(이전 약 870MB)였습니다.
  - 덤프만 읽는 외부 역공학 도구를 쓴다면 `SkyrimDiagHelper.ini`의 `DumpAllModuleCode=1`로 예전(v0.2.71)처럼 모든 모듈 코드를 담을 수 있습니다. 그러면 덤프 하나가 다시 0.5~0.9GB입니다.
- **덤프 폴더 전체 크기에 상한을 둡니다**(`MaxTotalDumpGB`, 기본 5GB, 0은 무제한). 넥서스 댓글에서 출력 폴더가 15GB라는 제보가 있었습니다. 지금까지는 종류별 개수(각 20개)로만 정리해서 기본값으로 약 40GB까지 쌓일 수 있었습니다. 이제 크래시·프리징·수동 덤프를 합쳐 상한을 넘으면 오래된 덤프부터 리포트와 함께 지웁니다.
- **전체 검수에서 찾은 문제 15건을 고쳤습니다.** 분석 결론에 영향을 주는 것은 세 가지입니다.
  - 다른 크래시의 것일 수 있는 Crash Logger 로그는 이제 원인 후보를 만들지 않습니다(근거 목록에 낮은 신뢰도 단서로만 남음).
  - 메인 스레드가 엔진·GPU·드라이버 안에서 기다린 프리징에서, 요약은 "스택의 플러그인을 빼지 말라"고 하는데 체크리스트는 같은 플러그인을 비활성화하라고 하던 모순을 고쳤습니다.
  - 1위와 2위 후보의 점수가 같으면 신뢰도가 이제 최대 "중간"입니다(지금까지는 점수만 높으면 "높음").
- 뷰어는 v0.2.71이 분석해 둔 덤프를 열 때 한 번 다시 분석합니다. 보관 덤프 31개로 비교했을 때 결과가 바뀐 것은 없었고, 위 세 가지에 해당하는 덤프만 달라집니다.

## 정정
- `SkyrimDiag.ini`의 `CrashHookMode=1` 설명("블랙리스트: 알려진 무해한 예외를 뺀 모든 예외를 기록")이 실제 동작과 달랐습니다. 실제로는 치명적 예외(접근 위반, 스택 오버플로, 힙 손상 등)를 기록하고, 처리된 C++ 예외·중단점 같은 그 밖의 코드는 아무도 처리하지 않았을 때만 기록합니다. 설명만 고쳤고 동작은 그대로입니다.
- 크래시 재수집(`EnableAutoRecaptureOnUnknownCrash`, 기본 꺼짐) 설명을 고쳤습니다. "fault module 미확정이 반복되면 FullMemory 덤프 1회"가 아니라, 같은 크래시가 기준 횟수만큼 반복되고 분석이 약할 때(fault module 미확정, 후보 충돌, 스택 해제 실패) 정보를 더 담은 덤프(`_Richer`)를, 약한 근거가 더 겹쳐 반복되면 전체 메모리 덤프(`_Full`)를 씁니다.

## 엔진 변경
**플러그인**
- 코드 변경 없음(버전만 올림).

**Helper**
- 덤프 범위(ADR-0023):
  - `DumpMode=1`의 크래시·프리징·수동 덤프는 게임 EXE 코드를 통째로 담고, 다른 모듈의 코드는 뺍니다. 디스크의 `SkyrimSE.exe`는 Steam DRM으로 코드가 암호화돼 있어 덤프 말고는 얻을 곳이 없고, SKSE 플러그인이 메모리에서 고친 후킹 지점도 덤프에만 남습니다.
  - 덤프를 쓸 때 각 스레드의 실행 위치(RIP, 크래시 덤프는 예외 위치도) 앞뒤 0x100바이트와, 스택 값이 가리키는 모듈 코드의 함수를 더 담습니다. 스택이 가리킨 모듈과 게임 EXE의 헤더·export·`.pdata`·unwind 정보도 담아 덤프만으로 콜스택을 풀 수 있게 합니다. 상한은 코드 8MB, 모듈 정보 16MB, 시간 200ms입니다(실게임 측정: 스택 코드 0.19\~0.26MB, 모듈 정보 10.2\~11.8MB, 36\~76ms).
  - 크래시 덤프에서 `MiniDumpWithModuleHeaders`를 뺐습니다. 이름과 달리 모든 모듈의 리소스·재배치·`.pdata`까지 약 290MB를 담았고, 분석기가 쓰는 export와 `.pdata`는 위 수집이 담습니다.
  - 크래시 재수집(`_Richer`, `_Full`), `DumpMode=2`, PSS 스냅샷 덤프는 예전처럼 모든 모듈 코드를 담습니다. 게임 EXE 주소를 얻지 못하면 모든 모듈 코드를 담고 로그에 남깁니다.
  - 기록: 매니페스트와 요약 JSON의 capture profile에 `code_segments_scope`(`none`/`all`/`game_and_stacks`), 리포트의 `CaptureProfileCodeSegments` 줄에 범위, 설정 스냅샷에 `dump_all_module_code`, 헬퍼 로그에 덤프마다 `Code memory:` 줄이 남습니다. 매니페스트는 설정값이 아니라 실제로 쓴 범위를 기록합니다.
- 덤프 폴더 상한(`MaxTotalDumpGB`):
  - 종류별 개수 정리를 먼저 하고 크기를 봅니다. 최신 덤프부터 담다가 넘치면 그 덤프와 그보다 오래된 덤프를 모두 지웁니다. 정리는 헬퍼가 시작할 때와 캡처 뒤에 합니다.
  - 항상 남기는 것: 가장 최근 캡처 1건, 하루가 지나지 않은 종류별 최신 캡처(게임을 끈 뒤 뷰어가 열 수 있게), 그리고 이 캡처들과 시각이 같은 덤프. 크래시 재수집 덤프는 이제 현재 시각이 아니라 원래 크래시의 시각을 이름에 써서, 원래 크래시 덤프와 함께 남습니다.
  - 지울 때 Summary·Report·Blackbox, WCT, ETL, incident manifest를 함께 지웁니다. 뷰어가 열어 둔 덤프처럼 지울 수 없는 것은 리포트도 남기고 다음 정리 때 다시 시도합니다.
  - incident manifest의 설정 스냅샷에 `max_total_dump_gb`를 더했습니다.
- 크래시 매니페스트는 실제로 쓴 덤프 프로필을 기록합니다. 다시 쓰기에 실패해 최소 덤프가 남은 경우에도 설정값을 기록하던 문제입니다.
- 덤프 쓰기가 실패하면 쓰다 만 파일을 지웁니다. 프리징·수동·재수집 경로는 이 파일을 남겨 뷰어 목록에 나왔습니다.
- WCT 대기 체인이 배열(16개)보다 길게 보고되면 배열 크기로 자릅니다. 스택 배열 밖을 읽었습니다.
- 크래시 버킷 통계와 요약 JSON에서 타입이 틀린 값은 없는 값으로 봅니다. 지금까지는 그런 값 하나로 헬퍼가 종료됐습니다. 통계를 쓸 때 잘못된 UTF-8은 치환합니다.
- 분석기·뷰어를 실행할 때 인자의 역슬래시를 바르게 인용합니다. `OutputDir=D:\`처럼 경로가 역슬래시로 끝나면 `--out-dir` 인자가 깨지고 `--headless`가 빠졌습니다.
- `AutoOpenCrashWaitForExitMs`·`AutoOpenHangDelayMs`를 헬퍼가 실제로 기다리는 최대 10초로 자릅니다. 매니페스트에 실제로 쓰인 값이 남습니다.

**분석기**
- 짝짓기가 모호한 Crash Logger 로그(다른 크래시의 것일 수 있음)는 후보를 만들지 않습니다. 지금까지는 가중치만 3으로 낮춰, 프레임 단서뿐인 후보가 "중간(reference_clue)"으로 요약과 다음 행동에 나왔습니다.
- 구경꾼 대기(메인 스레드가 엔진·GPU·드라이버 안에서 기다림) 프리징에서는 "[유력 후보] 업데이트/비활성화" 조언을 내지 않습니다. WCT가 잠금 소유 스레드를 지목했으면(한 번의 수집이라도) 요약이 그 스레드를 먼저 보여 주므로 예전처럼 스택 조언을 남깁니다.
- 1·2위 후보가 동점이면 신뢰도는 최대 Medium입니다. 코드 주석의 의도("High는 2위보다 확실히 앞설 때")와 실제 판정이 달랐습니다. 신뢰도 점수는 `AnalyzerScoringPolicy.h`로 옮기고, 테스트가 실제 함수를 부르게 했습니다.
- 덤프의 Memory64 목록 개수를 나눗셈으로 검사합니다. 개수가 2^60인 손상된 덤프는 곱셈이 넘쳐 검사를 통과했고, 분석 전체가 실패했습니다.
- Crash Logger 로그 줄의 플러그인 참조를 선형 시간에 찾습니다. 지금까지는 조작한 1MB 줄 하나로 몇 시간이 걸렸습니다.

**뷰어**
- `SkyrimDiagHelper.ini`를 헬퍼와 같은 규칙으로 읽습니다(BOM, BOM 없는 UTF-16LE, 엄격한 UTF-8, 그 밖은 ANSI 코드 페이지). UTF-8로만 읽어서, ANSI(CP949)로 저장한 한글 `OutputDir`을 헬퍼와 다른 폴더로 찾았습니다.

- ADR-0023: 덤프 범위의 근거(보관 덤프 31개를 PE 섹션 단위로 다시 본 결과), 시뮬레이션과 실게임 결과.
- 한국어 README에 영어판에만 있던 지원 버전·요구사항, 분석 캐시 정리, 스레드 덤프 안내를 더했습니다.

## 실게임에서 확인한 것
- 1.6.1170(MO2, 켜진 모드 약 4,366개)에서 덤프 범위와 폴더 상한이 들어간 시험 빌드(main `159cbfc`)로:
  - 2026-10-30, 첫 실행: 출력 폴더의 덤프 31개(21.67GB)를 최신 크래시 덤프 5개(4.23GB)로 줄였습니다.
  - 수동 캡처 5건: 58\~60MB. 덤프를 쓰는 시간은 1.5\~2.0초(이전 수동 캡처 2.2\~2.9초, 파일 시각으로 잰 추정이고 같은 장면은 아님). 헬퍼 로그 `Code memory:` 줄은 스레드 246\~249개, 스택 코드 0.19\~0.26MB, 모듈 42\~50개의 헤더·unwind 정보 10.2\~11.8MB, 수집 36\~76ms였습니다.
  - 게임 창을 닫는 중에 난 오류의 크래시 덤프 1건: 67MB. 리포트에 `CaptureProfileCodeSegments: 1 (game_and_stacks)`로 기록됐습니다.
  - 새 수동 덤프 1건과 크래시 덤프를 로컬 파일 사용과 덤프만 사용으로 각각 분석했고, 결과가 같았습니다. 크래시 콜스택은 덤프만으로도 모드 DLL 5개를 지나 12프레임까지 풀렸습니다.
- 실게임 미확인:
  - 새 범위로 쓴 프리징 덤프(자동 감지). 같은 범위의 프리징 덤프는 테스트 프로세스 자신의 덤프로만 확인했습니다.
  - `DumpAllModuleCode=1`과 크래시 재수집 덤프의 새 이름(테스트로만 확인).
  - 전체 검수 수정(#201, #202): 위 시험 빌드 뒤에 들어가 실게임에서 따로 보지 않았습니다. 테스트와 보관 덤프 31개 비교로 확인했습니다.

## 주의사항
- 이미 있는 덤프는 크기가 그대로입니다. 업데이트 직후에는 예전 큰 덤프가 상한의 대부분을 차지할 수 있고, 새 덤프가 쌓이면서 차례로 정리됩니다.
- `DumpAllModuleCode=1`, `DumpMode=2`, 크래시 재수집(`EnableAutoRecaptureOnUnknownCrash=1`)을 쓰면 덤프 하나가 0.5GB에서 몇 GB까지 커지므로 `MaxTotalDumpGB`를 함께 올려 주세요.
- WinDbg 같은 도구로 덤프를 직접 볼 때, 게임 EXE 밖 모듈의 코드는 스택이 가리킨 부분만 덤프에 있습니다. 나머지를 보려면 도구에 DLL 파일 경로를 지정하거나 `DumpAllModuleCode=1`로 캡처해 주세요.
