# v0.2.61-rc1 — 덤프에서 크래시 오브젝트 읽기와 Windows 업데이트 뒤 분석 유지

크래시 당시 게임 오브젝트를 덤프에서 직접 읽고, Windows 업데이트 뒤에도 덤프를 분석할 수 있게 한 테스트용 프리릴리즈입니다. 기존 파일 일부만 덮지 말고 ZIP 전체를 설치해 주세요.

## 핵심 변경
- CTD 리포트에 크래시 당시 레지스터와 스택이 가리킨 게임 오브젝트가 나옵니다. 예: `RCX: Character [0xFEAD081B] Skyrim.esm -> AE_StellarBlade_Doro.esp`. Crash Logger 로그가 없어도 됩니다.
- 덤프에 시스템 DLL과 그래픽 드라이버의 스택 해제 정보와 함수 이름표를 담아, Windows나 드라이버를 업데이트한 뒤에도 그 덤프의 스택을 끝까지 풀고 이름을 바르게 붙입니다.
- 같은 원인의 프리징(예: 같은 GPU 대기)을 한 버킷으로 묶어 반복 여부가 이어집니다.
- 리포트(146~193KB → 약 13KB)와 요약 JSON(1.6MB → 약 11KB)이 가벼워졌습니다.
- 한국어 리포트의 후보 안내에서 영어 용어를 우리말로 바꿨습니다.

## 엔진 변경
- Helper: CTD 순간 크래시 레지스터와 스택 위쪽 0x800바이트가 가리키는 오브젝트를 MSVC RTTI로 확인하고, 그 메모리를 덤프에 담습니다(최대 2MB). TESForm이면 FormID와 플러그인 파일 이름까지 담깁니다(ADR-0010).
- Helper: 모든 덤프에 Windows 폴더 아래 모듈의 PE 헤더, export 이름표, `.pdata`, 스택 해제 정보를 담습니다(최대 24MB, 약 17MB)(ADR-0011).
- 분석기: 덤프에서 오브젝트를 읽어 근거 항목(신뢰도 낮음), 리포트 `덤프 오브젝트:` 블록, 요약 JSON `dump_objects`로 보여 줍니다. 후보 선정에는 아직 쓰지 않습니다.
- 분석기: 로컬 DLL이 덤프와 다른 빌드면 쓰지 않고 덤프 안의 정보로 스택을 풀고 이름을 붙입니다.
- 분석기: 대기로 분류된 프리징의 버킷 키를 대기로 정합니다(`HANG1-`). 엔진·드라이버 대기와 modal 대화상자에서는 스택의 플러그인을 이력 후보로 기록하지 않습니다.
- 분석기: 리포트 이벤트를 개요 한 줄과 최근 60개로 줄이고, 요약 JSON의 플러그인 목록을 개수로 바꿨습니다.
- CI: PR의 Windows clang-tidy는 바뀐 `.cpp`만 검사합니다(`main`과 릴리즈는 항상 전체).

## 테스트 시 확인할 점
- 게임을 켜고 수동 캡처(`Ctrl+Shift+F12`)를 한 번 해 주세요. 덤프가 이전보다 약 17MB 커지고, Helper 로그와 리포트가 평소처럼 나오면 됩니다.
- 리포트 끝의 이벤트 부분이 "이벤트: N개, …" 한 줄과 최근 60개로 나오는지 봐 주세요.
- CTD가 나면 리포트의 `덤프 오브젝트:` 블록을 같은 크래시의 Crash Logger 로그(있다면)의 오브젝트 목록과 비교해 주세요.
- 프리징이 반복되면 두 번째부터 "같은 버킷 키" 근거가 붙는지 확인해 주세요.
- 아직 실게임에서 확인하지 못한 항목: 덤프 오브젝트(실제 CTD 필요), 대기 기반 프리징 버킷(실제 프리징 필요), Windows 업데이트 뒤 새 덤프 분석(다음 업데이트 필요), 모드의 assert로 난 CTD의 `ExceptionCode` `0x80000003`, AMX CPU에서의 CTD 덤프(CI에서만 확인).

## 주의사항
- Helper와 분석기가 바뀌었습니다. 플러그인 코드와 공유 메모리 프로토콜(SharedLayout v4)은 v0.2.60과 같지만 버전 정보가 바뀌므로 ZIP 전체를 교체해 주세요.
- 덤프 오브젝트와 시스템 DLL 정보는 이 버전으로 새로 찍는 덤프부터 들어갑니다.
- 덤프가 약 17MB 커지고, 캡처마다 시스템 DLL 정보를 읽는 시간이 조금 듭니다.
- 오브젝트 이름(NPC 이름 등)과 에디터 ID는 아직 읽지 않습니다.
- 새 프리징 버킷 키(`HANG1-`)는 이전 이력의 `CTD3-` 키와 합쳐지지 않습니다.
- 검수된 실사고 코퍼스가 없어 다른 로거 대비 적중률을 수치로 주장하지 않습니다.

- Windows production clang-tidy(`WarningsAsErrors`): 변경 파일 로컬 clean, 전체는 `main` CI 기준
- 덤프 오브젝트 e2e: 실제 Helper 크래시 덤프에서 `Character`, FormID, 플러그인 두 개를 읽어 냄. Helper가 메모리를 담지 않으면 실패

- Windows native RelWithDebInfo / WinUI self-contained publish: 성공 (`HEAD_SHA`)
- 로컬 패키징: `Tullius_ctd_loger_v0.2.61-rc1.zip` 생성 성공 (`--no-pdb`, `ZIP_BYTES` bytes, ZIP_ENTRIES entries, PDB 0개)
- Release hard gate(clean provenance 강제): `OK` — 버전·x64·바이너리 메타데이터와 commit-bound provenance 일치, 패키지의 최상위 WinUI 런처로 유효 minidump 분석 smoke 통과
