# v0.2.74 — 불러오던 세이브 기록과 세이브 손상 판단, 읽기 쉬운 리포트

어떤 세이브를 불러오다 튕겼는지 기록하고, 같은 세이브가 불러올 때마다 다른 곳에서 실패하면 세이브 손상을 먼저 의심하도록 한 릴리즈입니다. 텍스트 리포트의 순서와 잡음을 정리했고, 내부 구조도 함께 정리했습니다. SKSE 플러그인, Helper, 분석기, 뷰어가 모두 바뀌었으니 ZIP 전체를 설치해 주세요(SharedLayout protocol은 그대로 v4, 블랙박스 이벤트 종류만 추가). MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요. 새 설정은 없습니다.

## 한눈에 보기
- **어떤 세이브를 불러오다 튕겼는지 기록합니다**(ADR-0025). 플러그인이 세이브 불러오기의 시작과 끝을 블랙박스에 남기고, 리포트에 `세이브:` 줄로 보여 줍니다.
  - 계기: 11/01 같은 세이브를 두 번 불러왔고 두 번 다 로딩 중에, 매번 다른 곳에서 튕겼습니다. 리포트는 그 순간 보인 모드(SPID, LEZ)를 짚었지만, 그 전 세이브와 새로 만든 세이브는 잘 열렸습니다. 실제 단서는 "같은 세이브에서만, 매번 다른 곳에서"였는데, 어떤 세이브였는지 기록이 없어 볼 수 없었습니다.
- **같은 세이브가 불러올 때마다 다른 곳에서 튕기면 "세이브 손상 의심"을 먼저 알려 줍니다.** 빠른 답, 결론 문장, 다음 조치가 이 세이브를 앞세웁니다. 아래를 모두 만족할 때만 냅니다.
  - 크래시이고, 같은 세이브를 불러오다 난 이전 사고가 있습니다.
  - 위치를 확인한 실패 장소(오류 모듈과 오프셋, 모듈이 없으면 실패 양상)가 이번 것까지 2곳 이상입니다.
  - 그 사이 다른 세이브를 불러오다 난 사고가 없습니다.
  - 해결 방법이 있는 알려진 원인이나 설치 중인 후킹이 있으면 그것을 앞세웁니다.
  - 순서는 덤프의 캡처 시각으로 정하고, 같은 덤프의 사본은 한 번만 셉니다. 한 번 불러오는 동안 찍힌 자동 프리징 캡처와 그 불러오기를 끝낸 크래시도 한 번의 실패로 셉니다.
  - "이 세이브가 깨졌다"고 단정하지 않습니다. 모드 버그가 그 세이브의 데이터에서만 날 수도 있어서, 이전 세이브가 열리는지와 문제 세이브에서만 반복되는지 확인하도록 안내합니다.
- **텍스트 리포트를 읽기 쉽게 정리했습니다.**
  - 권장 조치가 근거 바로 뒤에 옵니다. 전에는 최근 리소스 120줄 남짓 뒤에 있었습니다.
  - 프리징·수동 캡처 리포트에 빈 예외 블록(`ExceptionCode: 0x0`)을 쓰지 않습니다.
  - 설치에 관한 안내(플러그인 슬롯 한계, SKSE가 로드하지 못한 DLL, 같은 파일을 여러 모드가 제공함, 캡처 프로필)는 근거에서 빼 "설치 환경 메모"로 따로 모읍니다.
  - 최근 리소스는 40개만 쓰고, 연달아 나오는 스레드 생성·종료와 모듈 로드 이벤트는 한 줄로 묶습니다.
  - 모드팩이 붙인 이름 접두어(`[NoDelete] 0444 …`)를 사람이 읽는 곳에서 뗍니다.
  - 권장 조치가 텍스트 리포트에는 없는 뷰어의 "탭"만 가리키지 않고, 리포트의 해당 부분도 함께 적습니다.
- **`CrashHookMode` 오타로 크래시 훅이 꺼지거나 위험한 모드 2가 켜지지 않습니다.** 숫자가 아닌 값은 0(크래시 훅 끄기)으로 읽혔고, `3`·`99` 같은 범위 밖 값은 동의 설정 없이 모든 예외 기록 모드(2)가 됐습니다. 이제 0·1·2만 인정하고 다른 값은 기본값 1로 읽습니다. 모드 2는 `EnableUnsafeCrashHookMode2=1`일 때만 켭니다. 값이 잘못됐으면 `SkyrimDiag.log`에 경고를 남깁니다. 기본 설정(`CrashHookMode=1`)으로 쓰는 경우는 영향이 없었습니다.
- 뷰어는 v0.2.73이 분석해 둔 덤프를 열 때 한 번 다시 분석합니다.

## 엔진 변경
**플러그인**
- SKSE `kPreLoadGame`에서 블랙박스 이벤트 `SaveLoadStart`(22), `kPostLoadGame`에서 `SaveLoadEnd`(23)를 남깁니다. `SkyrimDiag.log`에 불러온 세이브 이름과 끝났는지, 새 게임 시작을 한 줄씩 남깁니다. 이벤트 종류만 추가했고 공유 메모리 배치는 그대로라 protocol은 v4입니다.
- `CrashHookMode`와 `EnableUnsafeCrashHookMode2`를 글자로 읽어 엄격하게 판정합니다(값 뒤의 공백과 `;`·`#` 주석은 허용).

**Helper**
- 수동 캡처와 프리징 캡처가 같은 공통 경로(WCT 수집, PSS 스냅샷, 재수집 판정, 덤프 쓰기, 사고 기록 문맥)를 씁니다. 프리징 캡처도 이제 WCT 수집 실패를 Helper 로그에 남깁니다(전에는 콘솔에만 출력).
- 크래시 이벤트 처리(약 500줄)를 단계별 함수로 나눴습니다. 프리징 판정 기준 공식과 WCT 교착 판정도 한 곳으로 모았습니다. 동작은 같습니다.

**분석기**
- 세이브 판단(ADR-0025):
  - 마지막 `SaveLoadStart` 뒤에 `SaveLoadEnd`가 없으면 "불러오는 중"으로 봅니다.
  - 크래시 기록에 불러오던 세이브, 실패 위치(`loading_fault_place`), 덤프 캡처 시각(`capture_unix`)을 남기고, 다음 분석이 같은 세이브의 이전 사고와 실패 장소를 셉니다.
  - 실패 위치를 모르는 기록(이전 시험판의 기록, 대기 버킷이 빈 프리징 등)은 실패 횟수에만 넣고 장소 수에는 넣지 않습니다. 이때 근거에 "위치를 확인한 사고만 장소 수에 포함했습니다."를 붙이고, "매번 같은 곳" 안내도 내지 않습니다.
  - 리포트에 `세이브:` 줄, 요약 JSON에 `save_load`를 넣고, 블랙박스 이벤트 이름과 세부 내용(`save=…`, `loaded`/`failed`)을 표시합니다.
  - `[세이브 손상]` 줄은 즉시 조치이고, 다음 조치 순위는 알려진 원인 바로 다음입니다.
- 리포트 정리(위 "한눈에 보기"). 근거 항목에 `setup_note` 표시를 두고 텍스트 리포트에서 따로 모읍니다.
- 같은 근거를 화면마다 다른 말로 부르던 것을 맞췄습니다: 반복 이력(전에는 "버킷 반복", "반복 기록"), 스택 분석(전에는 "실행 가능한 스택"), 근처 리소스 제공 모드.
- (내부) 다음 조치 선택이 뷰어의 권장 조치 분류와 같은 태그 판정을 씁니다. 근거·체크리스트·요약·빠른 답이 "누구를 지목할지"의 입력을 한 번만 계산해 같은 값을 읽습니다. 출력은 바뀌지 않습니다.

**뷰어**
- 근거 종류 이름을 분석기와 맞췄습니다(스택 분석, 근처 리소스 제공 모드). 스택 스캔만 있는 후보에 "Tullius 콜스택"이라는 이름을 붙이지 않습니다.
- 세이브를 불러오다 난 덤프의 저장된 분석은, 그 뒤 같은 출력 폴더의 세이브 이력(`crash_history.json`)이 바뀌었으면 다시 열 때 새로 분석합니다. 나중에 난 덤프를 먼저 열고 앞선 덤프를 분석한 경우, 예전 판단(세이브 손상 의심 없음)이 그대로 보이던 문제입니다.

**릴리즈·문서**
- (내부) 정확도 벤치마크가 후보 순위와 빠른 답을 따로 채점하고, 검토자가 단 빠른 답의 진단·권장 행동 정답도 채점합니다. 분석 비교 도구(`compare_analyses.py`)가 실제로 고른 다음 조치까지 비교합니다.
- (내부) Windows CI 작업 네 개의 준비 단계를 공용 action 하나로 모았고, 테스트의 파일 읽기와 해시 도우미를 하나로 정리했습니다.
- ADR-0025(세이브 불러오기 중 크래시). README 해석 안내에 한 줄씩 더했습니다.

## 주의사항
- 세이브 판단은 v0.2.74 플러그인이 기록한 덤프부터 동작합니다. 이전 버전의 덤프에는 불러오던 세이브가 기록돼 있지 않습니다.
- "세이브 손상 의심"은 확정이 아닙니다. 이전 세이브가 열리는지, 문제 세이브에서만 반복되는지 확인해 보세요. 이전 세이브도 열리지 않으면 모드 구성 쪽일 가능성이 큽니다.
- 이미 분석해 둔 덤프는 뷰어에서 열 때 한 번 다시 분석하므로, 처음 열 때만 조금 오래 걸립니다.
