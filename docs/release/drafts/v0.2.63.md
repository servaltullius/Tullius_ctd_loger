# v0.2.63 — 엉뚱한 DLL 지목 수정과 알려진 원인

실사고 CTD 두 건에서 리포트가 엉뚱한 DLL을 지목한 문제를 고치고, 원인이 알려진 크래시를 바로 알려 주는 분석기 릴리즈입니다. 게임에 들어가는 플러그인과 Helper의 코드는 v0.2.62와 같고, 분석기와 뷰어만 바뀌었습니다.

## 한눈에 보기
- **게임 스레드 시작 지점의 훅을 후보에서 제외** — 게임 스레드의 시작 지점만 감싸는 플러그인(이번 사례: `NPCWaterAIFix.dll`, `Trails.dll`)은 그 스레드의 모든 콜스택에 나타날 뿐 원인이 아닙니다. 콜스택 점수, Crash Logger 신호, 스택 스캔에서 빼고 근거 항목으로 설명합니다(ADR-0015).
- **알려진 원인 `[알려진 원인]`** — 같은 PC에서 1.7.104를 실행해 `ContentCatalog.txt`가 1.7 형식으로 바뀐 뒤 1.6.1170이 시작 직후 꺼지는 CTD를 알아보고, 파일을 휴지통으로 옮기라고 안내합니다. 이 태그는 다음 조치의 맨 앞에 옵니다.
- **후킹 설치 경쟁** — 어떤 모드가 게임 실행 중에 후킹을 설치하던 순간 다른 스레드가 반쯤 써진 코드를 실행한 CTD를 덤프에서 알아보고, 그 모드를 신뢰도 높음으로 짚습니다(이번 사례: Typing Mode, ADR-0016). 이전 리포트는 SkyrimUpscaler와 음악 모드를 지목했습니다.
- **알려진 크래시 지점 `[알려진 크래시 지점]`** — 공개된 수정 모드가 막아 주는 엔진 위치를 알아봅니다. 근거를 직접 확인한 것만 넣었습니다.
  - Engine Fixes의 FaceGen·ShadowSceneNode null 크래시(1.5.97·1.6.640·1.6.1170, 패치가 막는 정확한 주소일 때만)
  - 1.6.1170 물 반사 `AddWater`, 1.7.104 지오메트리 없는 NiTriShape, 1.5.97 A0D789, C++ 메모리 할당 실패(`std::bad_alloc`)
- **콜스택이 중간에 끊긴 경우 알림** — 스택 해제가 스레드 시작 전에 멈추면 그 이유(해제 정보 없음, 데이터 주소, 모듈 밖 주소)와 깊이를 근거 항목과 요약 JSON에 적습니다. 끊긴 주소나 크래시 주소가 이미 언로드된 DLL 자리면 그 이름도 적습니다.
- **프리징: 대기와 실행 구분** — 막힌 게임 스레드가 플러그인 안에서 기다리는지, CPU를 쓰며 도는지 구분합니다.

## 실게임에서 확인한 것
- 한 사용자의 MO2 환경(1.6.1170, SKSE 2.2.6, Crash Logger 1.25)
- 실사고 CTD 두 건을 새 분석기로 재분석
  - 2026-10-13 ContentCatalog CTD: 결론이 `CONTENT_CATALOG_FORMAT_MISMATCH`, 다음 조치가 ContentCatalog.txt를 휴지통으로 옮기기로 바뀌었고, 후보는 0개입니다. 파일을 옮기자 실제로 정상 실행됐습니다.
  - 2026-10-13 Typing Mode CTD: 결론과 다음 조치가 `Typing Mode (zzzz_TypeMode.dll)`(신뢰도 높음)로 바뀌었습니다. 모드 로그에 크래시와 같은 밀리초의 후킹 설치 기록이 있습니다.
- 크래시 테스트(개발용 플러그인, 배포하지 않음): 이벤트 콜백 안의 접근 위반, 플러그인 자신의 스레드, 무한 재귀(스택 오버플로), CPU를 도는 프리징, 이벤트 콜백 프리징 5건을 추가로 일으켜 원인 DLL을 후보로 짚는 것을 확인했습니다.
- 테스트 빌드 설치 후 정상 실행과 정상 종료(Helper 연결, 사전 점검 경고 0)
- 실게임 미확인
  - 새 알려진 크래시 지점 시그니처가 실제 사고에서 일치하는 것(보관 덤프에는 해당 사고가 없음)
  - 1.7.104·1.5.97·1.6.640의 실제 CTD

## 주의사항
- 플러그인(`SkyrimDiag.dll`)과 Helper의 코드는 v0.2.62와 같습니다. 그래도 분석기와 데이터 파일이 바뀌었으니 ZIP 전체를 교체해 주세요.
- 알려진 크래시 지점은 "그 자리에서 터졌다"는 뜻입니다. 그 앞에서 잘못된 데이터를 만든 모드는 이 패턴만으로 알 수 없습니다.
- 후킹 설치 경쟁은 타이밍에 따라 나는 크래시라, 한 번 다시 실행해 괜찮다고 해결된 것은 아닙니다.
- 측정용 사례 대부분이 크래시 테스트라 다른 크래시 로거 대비 적중률을 수치로 주장하지 않습니다.

## 개발
- 정확도 측정 도구 `scripts/accuracy_benchmark.py`와 분석기 CLI 옵션 `--no-crash-logger`. 원인을 확인한 사고를 분석기 단독, 분석기+Crash Logger, Crash Logger 단독의 세 가지로 채점합니다.
- 크래시 테스터 시나리오 F7~F11.
- 릴리즈 전 검수(Claude, Codex)에서 찾은 10건을 고쳤습니다. 끊긴 콜스택을 완전한 것으로 본 판정, Crash Logger의 모듈 없는 프레임, 실제 로그에서 일치할 수 없던 `CPP_BAD_ALLOC` 등입니다.
- PowerShell에서 ctest를 돌리면 WSL bash를 골라 실패하던 CI 배선 테스트를 고쳤습니다.
