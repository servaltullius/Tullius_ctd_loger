# v0.2.81-rc1 — 다른 예외를 처리하던 중 난 크래시 읽기, 스택 오버플로 앞단 가드, 기록 없는 종료의 Windows 오류 위치

v0.2.80 이후의 변경(PR #358, #359, #360)을 모은 테스트용 프리릴리즈입니다. 플러그인, Helper, 분석기가 바뀌었고, 뷰어 화면의 코드는 v0.2.80과 같습니다(SharedLayout protocol v4 그대로, 새 설정 없음). 뷰어 안의 분석 DLL은 분석기와 같이 바뀝니다. ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

버전 번호가 0.2.81로 올라서, v0.2.80 이전 버전이 분석해 둔 덤프는 뷰어에서 열 때 한 번 다시 분석합니다.

## 한눈에 보기
- **다른 예외를 처리하던 중 난 크래시를 알아봅니다(ADR-0039).**
  - 2026-11-28 실제 사례: 업스케일러 모드에 딸린 프레임 생성 DLL(`nvngx_dlssg.dll`)이 맨 앞에 등록한 예외 처리기가 `Precision.dll+0xe5547`의 메모리 읽기 오류를 먼저 받았습니다. 그 처리기 안에서 이미 망가진 힙이 힙 손상(`0xC0000374`)으로 터졌고, Crash Logger 로그는 남지 않았습니다. v0.2.80의 리포트는 `nvngx_dlssg.dll`을 첫 용의자로, `Precision.dll`을 둘째로 짚었고, 먼저 난 오류는 어디에도 나오지 않았습니다.
  - Windows는 하드웨어 예외를 처리기에 넘길 때, 예외가 난 스레드의 스택에 그 예외의 레지스터(CONTEXT)와 예외 정보(EXCEPTION_RECORD)를 남깁니다. 이제 분석기가 크래시 스레드의 스택에서 그것을 읽어, 처리 중이던 예외가 난 모듈을 먼저 의심합니다(가능성은 최대 중간). 처리기 쪽에만 있는 모듈은 그 뒤에 낮음으로 둡니다.
  - 그 덤프를 다시 분석하면 빠른 답이 `Precision.dll`을 첫 용의자(가능성 중간)로 두고, "어떻게 튕겼나: Precision.dll에서 메모리를 읽다가 먼저 오류가 났고, 게임은 그 오류를 처리하던 nvngx_dlssg.dll 안에서 튕겼습니다(힙 손상)."라고 씁니다. 결론은 `[예외 처리 중 크래시] Precision.dll+0xe5547에서 메모리 읽기 오류(0xC0000005, 주소 0x1DFD5DF3000)가 먼저 났고, …`로 시작합니다.
- **스택 오버플로를 다른 모드의 예외 처리기보다 먼저 기록합니다(ADR-0037).**
  - 2026-11-27 rc3 시험에서 크래시 테스터의 스택 오버플로(Ctrl+Shift+F9)가 덤프도 Crash Logger 로그도 남기지 않았습니다. 같은 프레임 생성 DLL이 Tullius보다 나중에 맨 앞에 예외 처리기를 등록했고, 그 처리기가 넘친 스택의 남은 여유를 다 써서 게임이 끝난 것으로 봅니다.
  - 이제 플러그인이 스택 오버플로만 다루는 처리기를 하나 더 두고, SKSE가 플러그인을 다 불러온 뒤와 입력·데이터 로드, 새 게임, 세이브 로드 때 그것을 다시 맨 앞에 올립니다. 스택 오버플로가 나면 이 처리기가 먼저 기록하고, Helper가 덤프를 쓸 때까지(최대 5초) 그 스레드를 붙잡은 뒤 다음 처리기로 넘깁니다. 그 뒤 앞자리 처리기가 게임을 끝내도 덤프는 남습니다.
- **기록된 크래시 없이 끝난 게임은, Windows가 적은 오류 위치를 Helper 로그에 남깁니다(ADR-0038).**
  - 게임이 0이 아닌 종료 코드로 끝났는데 Tullius가 크래시를 기록하지 못했으면, Helper 로그에 종료 코드 말고는 단서가 없었습니다(위의 스택 오버플로, 처리기를 거치지 않는 즉시 종료 등).
  - 이제 Windows 오류 보고가 Application 로그에 남긴 그 게임 프로세스의 이벤트 1000을 찾아 `SkyrimDiagHelper.log`에 한 줄을 씁니다. 예: `Windows Error Reporting recorded this exit (Application log, event 1000): exception 0xc0000005 in ntdll.dll 10.0.26100.9974 at offset 0x55ae0. That is where the process ended, not necessarily where the problem began.`
  - 이 위치는 프로세스가 끝난 곳이지, 문제가 시작된 곳이 아닐 수 있습니다.

## 수정
**플러그인**
- 스택 오버플로 전용 벡터 예외 처리기(`StackOverflowFrontGuard`)를 `CrashHookMode` 1·2에서 둡니다. 스택 오버플로가 아닌 예외는 공유 메모리를 건드리지 않고 바로 넘깁니다.
- 가드는 지금과 같은 크래시 기록을 쓰고, 이 호출이 기록을 썼을 때만 Helper의 덤프 완료 신호를 그때 열어 최대 `min(UnhandledCrashHoldMs, 5000)`ms 기다립니다. Helper가 없거나 예전 버전이면 붙잡지 않습니다. 가드가 있으면 기존 벡터 처리기는 스택 오버플로를 건너뜁니다.
- SKSE 메시지 `kPostLoad`, `kPostPostLoad`, `kInputLoaded`, `kDataLoaded`, `kPostLoadGame`, `kNewGame` 때 가드를 다시 맨 앞에 등록하고 앞의 등록을 지웁니다. 가드 안에 스레드가 있으면 건너뜁니다. `SkyrimDiag.log`에는 데이터 로드 때 한 번 결과(`SkyrimDiag: stack overflow front guard moved to front` 등)를 적습니다.

**Helper**
- 0이 아닌 종료 코드로 끝났고 크래시 기록이 없을 때(종료 중 멈춤으로 본 경우, 응답하지 않다가 끝난 경우, 기록된 크래시 없는 비정상 종료), Application 로그의 이벤트 1000(`Application Error`)에서 PID와 프로세스 생성 시각이 이 게임과 같은 것을 찾아 한 줄을 씁니다. Windows가 응답 없음으로 닫은 경우(`0xCFFFFFFF`)와 이미 기록된 크래시가 있는 경우는 찾지 않습니다.
- 최근 10분, 최신부터 한 건씩 최대 200건, 읽기 시간 500ms 안에서 찾습니다. NTSTATUS 오류 종료에서 못 찾으면 1초 뒤 한 번 더 찾습니다. 조회가 실패하거나 예외가 나도 종료 처리는 끝까지 갑니다.
- 모듈 경로, 컴퓨터 이름, 사용자 SID는 옮기지 않습니다. 기존 줄과 WER 안내 파일은 그대로이고, 새 설정은 없습니다.

**분석기**
- 크래시 스레드의 스택워크가 `ntdll!KiUserExceptionDispatcher` 프레임을 지나면, 그 프레임의 스택 포인터에 있는 CONTEXT(64비트 사용자 모드, Rip이 다음 프레임과 같음)와 그 뒤의 EXCEPTION_RECORD(같은 주소, 오류 등급 코드)를 읽습니다. 덤프의 예외 컨텍스트에서 시작한 워크만 보고, 디스패처가 여럿이면 가장 깊은(처음) 예외를 씁니다.
- 용의자: 처리 중이던 예외의 콜스택을 먼저 매기고 맨 위는 최대 중간, 처리기 쪽에만 있는 모듈은 그 뒤 낮음입니다. 행동 우선 후보도 같은 상한을 따릅니다. 짝지어진 Crash Logger 로그는 처리기 안의 예외를 기록하므로, 처리기 쪽에만 있는 모듈을 가리키는 그 로그의 프레임 신호는 쓰지 않습니다.
- 출력: 결론 앞말 `[예외 처리 중 크래시]`, 빠른 답의 이유와 "어떻게 튕겼나" 줄, 근거 `다른 예외를 처리하던 중 난 크래시`, 리포트의 `처리 중이던 예외:` 줄과 그 예외의 콜스택(8프레임), 요약 JSON `exception.earlier_exception`.
- 보고된 예외(예외 코드, 위치, 예외 명령어), 크래시 버킷, 알려진 패턴 매칭은 그대로입니다.

**문서(내부)**
- ADR-0037, ADR-0038, ADR-0039와 ADR 목록, `README.md`·`docs/README_KO.md`의 출력 위치와 판단 기준 설명에 한 줄씩.
- 넥서스 설명의 v0.2.80 반영(PR #357)과 v0.2.80 배포 날짜(PR #356).

## 주의사항
- 가드를 마지막으로 다시 올린 뒤(세이브 로드·새 게임 이후) 맨 앞에 처리기를 등록한 모드는, 다음에 다시 올릴 때까지 가드보다 앞에 섭니다.
- 붙잡기가 끝난 뒤 앞자리 처리기가 게임을 끝내면, 덤프는 남지만 Crash Logger 로그는 여전히 남지 않습니다. 스레드 스택 여유는 늘리지 않았습니다.
- 앞자리 처리기가 스택 오버플로가 아닌 예외에서 프로세스를 끝내는 경우(자기 덤프를 쓰고 바로 종료)는 바뀌지 않습니다.
- WER 줄은 Windows 오류 보고가 켜져 있고 이벤트 1000을 남기는 종료에서만 나옵니다. `TerminateProcess`로 끝났거나 응답 없음으로 닫혔으면 없고, 이벤트가 종료 뒤 약 2초보다 늦게 기록돼도 없습니다. 그 줄 때문에 Helper의 종료 처리가 최대 약 2초 늦어질 수 있습니다.
- `[예외 처리 중 크래시]`는 하드웨어 예외(접근 위반 등)를 처리하던 중의 크래시만 알아봅니다. C++ 예외를 처리하던 중(`catch` 안)의 크래시는 알아보지 못합니다. 처리 중이던 예외가 원래 처리될 예외였는지는 덤프로 알 수 없어서, 그 모듈도 가능성 중간까지만 둡니다.
- `v0.2.81-rc1`은 정식 `v0.2.81` 전에 확인하기 위한 테스트용 프리릴리즈입니다.
