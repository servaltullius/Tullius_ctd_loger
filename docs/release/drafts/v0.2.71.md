# v0.2.71 — X 버튼·창 닫기 기록 수정

v0.2.70의 창 닫기 기록을 고친 릴리즈입니다. 코드는 SKSE 플러그인(`SkyrimDiag.dll`)만 바뀌었지만, 버전이 맞아야 하므로 ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

## 한눈에 보기
- **X 버튼이나 작업 표시줄의 "창 닫기"로 게임을 끈 것을 이제 창 닫기로 기록합니다.** v0.2.70은 창 닫기를 보는 훅을 게임이 데이터를 불러오는 스레드에서 걸었는데, Windows는 훅을 건 스레드가 끝나면 그 훅을 지웁니다. 그 스레드는 메인 메뉴가 뜬 직후 끝나므로 v0.2.70의 창 훅은 실제 게임에서 동작하지 않았습니다. 이제 게임 창 스레드에서 훅을 겁니다.
  - v0.2.70에서도 이렇게 끄다 난 오류는 강제 종료(CTD 아님)로 분류됐습니다. 게임이 창 닫기를 받고 켜는 종료 플래그로 잡혔기 때문입니다. 다만 종류가 그때 열린 메뉴에 따라 "메뉴의 종료"(`game_quit`)나 "그 밖의 강제 종료"(`forced_quit`)로 나왔고, 이제 "창 닫기"(`window_close`)로 나옵니다.
- 뷰어는 v0.2.70이 분석해 둔 덤프를 열 때 한 번 다시 분석합니다. 분석기는 바뀌지 않았으므로 결과는 같습니다.

## 정정
- v0.2.70 노트의 "게임 창 스레드의 관찰 전용 훅(`WH_GETMESSAGE`, `WH_CALLWNDPROC`)으로 X 버튼과 다른 프로그램의 닫기 요청을 봅니다"는 실제로는 동작하지 않았습니다(위 설명). v0.2.70 노트의 실게임 미확인 목록에 있던 X 버튼을 확인하다 찾았습니다. 덤프에서 게임 창 스레드에 이 플러그인의 훅이 없었고, 그 테스트에서 작업 표시줄 닫기와 게임 창에 보낸 `SC_CLOSE`는 종료 플래그로만 `game_quit`으로 기록됐습니다.

## 엔진 변경
**플러그인**
- 창 훅은 하트비트 작업이 게임 창 스레드에서 처음 돌 때(메인 메뉴가 뜬 뒤) 그 스레드에서 겁니다. 창이 다른 스레드에서 다시 만들어지면 그 스레드에서 다시 겁니다. 키 샘플과 종료 플래그 읽기는 예전처럼 데이터 로드(`kDataLoaded`)에 시작합니다.
- `SkyrimDiag.log`: 시작 줄이 `close request log on (key sampler, quit flag; window hooks from the game window's thread)`로 바뀌었고, 훅을 기다리면 `window hooks wait for the game window's thread N (heartbeat task on thread M)`, 걸면 `window hooks on (game window thread N)`, 거부되면 `window hooks refused (…)`가 남습니다. `close request log off` 경고에 상관없는 오류 코드가 찍히던 문제도 고쳤습니다.
- 창 닫기(`SC_CLOSE`, `WM_CLOSE`)는 게임 창 자체에 온 것만 셉니다. 다른 플러그인이 자기 자식 창을 닫는 것은 게임 종료가 아니므로, 그 뒤 10초 안의 진짜 CTD를 강제 종료로 잘못 분류하지 않습니다. Alt+F4 키 메시지는 예전처럼 게임 창의 자식(포커스 창)에 온 것도 봅니다.
- 훅 안에서 게임의 `Main` 객체를 읽지 않고, 하트비트 작업이 마지막으로 본 게임 창과 비교합니다. 종료 정리 중 `Main`이 해제된 뒤에도 창은 메시지를 받을 수 있는데, 그때 읽다 오류가 나면 크래시 처리기가 그것을 크래시로 기록하기 때문입니다.
- `PeekMessage`의 `PM_REMOVE`를 비트로 확인해 `PM_REMOVE | PM_NOYIELD`로 꺼낸 메시지도 봅니다. 스카이림이 직접 하는 호출은 `PM_REMOVE`만 넘기므로 지금 게임에서 달라지는 것은 없습니다.

**Helper·분석기·뷰어**
- 코드 변경 없음(버전만 올림).

**문서**
- ADR-0022: 원인과 근거, 새 설치 방식.
- ADR-0021: 1.5.97 엔진 잠금 교착 시그니처를 복호화한 1.5.97 실행 파일과 대조한 결과(스택 위치가 모두 실제 호출 직후이고, 잠금 주소를 쓰는 함수가 스택의 함수와 맞음)와 v0.2.70 때의 실게임 잠금 메모리 수집을 기록했습니다.

## 실게임에서 확인한 것
- 1.6.1170(MO2, 켜진 모드 약 4,366개)에서 이 릴리즈와 같은 플러그인 코드의 시험 빌드로:
  - 2026-10-29 10:14, 메인 메뉴: 데이터 로드 때 `window hooks wait for the game window's thread 35484 (heartbeat task on thread 30148)`, 약 4초 뒤 `window hooks on (game window thread 35484)`. 게임 창에 `SC_CLOSE`를 보내자 76ms 뒤 `close request seen: window_close (WM_SYSCOMMAND SC_CLOSE posted)`, 종료 중 오류는 리포트 `분류: 강제 종료 (CTD 아님; window_close, 오류 0.0초 전)`, 뷰어 안 뜸.
  - 12:41, 플레이 중 일지에서 종료: `close request seen: game_quit (quit flag, Journal Menu open)`, 오류 없이 정상 종료(종료 코드 0).
  - 12:47, 플레이 중 전체 창 모드에서 작업 표시줄 "창 닫기": `close request seen: window_close (WM_SYSCOMMAND SC_CLOSE sent)`. 블랙박스에는 창 닫기, 9.5ms 뒤 종료 플래그, 6.6ms 뒤 종료 중 오류 순서로 남았고, 리포트 `분류: 강제 종료 (CTD 아님; window_close, 오류 0.0초 전)`, 뷰어 안 뜸.
- 실게임 미확인: 창 모드에서 X 버튼 직접 클릭(작업 표시줄 닫기와 같은 `WM_SYSCOMMAND` 경로), 훅이 켜진 채 Alt+F4, 다른 프로그램이 보낸 `WM_CLOSE`, 훅이 켜진 채 오래 플레이할 때의 체감 성능(짧은 세션 세 번만).

## 주의사항
- 처음 데이터를 불러오는 동안(메인 메뉴가 뜨기 전)의 X 버튼·창 닫기는 훅이 아직 없어 예전처럼 종료 플래그로만 기록됩니다.
- Engine Fixes의 safe exit처럼 종료를 고르자마자 프로세스를 끝내는 환경에서는, 메뉴로 종료해 오류 없이 꺼졌을 때 `SkyrimDiag.log`에 닫기 요청 줄이 남지 않을 수 있습니다(위 12:41에는 남았고, v0.2.70 때 한 번은 남지 않았음). 종료 중 오류가 나면 오류 순간에 종료 플래그를 다시 읽으므로 분류에는 영향이 없습니다.
- 다른 창·오버레이 모드와 충돌이 의심되면 `SkyrimDiag.ini`의 `EnableCloseRequestLog=0`으로 닫기 요청 기록을 끌 수 있습니다. 끄면 Alt+F4나 창 닫기 뒤의 오류도 예전처럼 CTD로 보고합니다.
