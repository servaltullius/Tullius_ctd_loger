# v0.2.70 — 알려진 크래시 늘림과 "어떻게 튕겼나" 설명, 엔진 잠금 교착 감지, Alt+F4 강제 종료 구분

v0.2.70-rc1~rc3를 묶어 정식으로 내는 릴리즈입니다. rc3 이후에는 게임 메뉴로 종료할 때의 닫기 요청 기록을 고쳤습니다(플러그인, 아래 "rc3 이후 바뀐 것"). 플러그인과 Helper, 분석기, 뷰어가 바뀌었으니 ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

## 한눈에 보기
- **수정 모드가 있는 1.6.1170 크래시를 더 알아봅니다.** 크래시 지점이 아래와 같으면 빠른 답이 "알려진 키보드 입력 크래시와 일치합니다"처럼 시작하고 해결 방법을 안내합니다. 수정 모드가 이미 로드된 채로 같은 크래시가 났으면 새 버전 확인이나 제작자에게 알리기를 안내합니다.
  - 키보드 입력 크래시(`SkyrimSE.exe+0xCDE0AE`): [Keyboard Offset Crash Fix SE-AE](https://www.nexusmods.com/skyrimspecialedition/mods/187246)
  - 물리 엔진(Havok) 계산 크래시 2곳과 정리 크래시 3곳: [Havok Solver Crash Fix - SKSE](https://www.nexusmods.com/skyrimspecialedition/mods/194392)
  - 물 충돌 크래시(`SkyrimSE.exe+0x51E220`, `+0x51E253`): [Water Collision Crash Fix NG](https://www.nexusmods.com/skyrimspecialedition/mods/190886)
  - 함정 접촉 크래시(`SkyrimSE.exe+0x3FF101`): 액터가 닿아 있던 함정 오브젝트가 사라진 뒤 엔진이 그 함정을 계속 처리하다 튕깁니다. Calamity 2(`CalamityAffixes.dll`)가 로드되어 있으면 2.2.6 이상으로 업데이트하라고 안내합니다.
- **접근 위반 크래시에서 게임이 무엇을 하다 튕겼는지 쉬운 말로 알려 줍니다.** 빠른 답에 "어떻게 튕겼나: 이미 사라졌거나 만들어진 적 없는 오브젝트를 쓰다가 튕겼습니다(null 포인터)." 같은 줄이 생기고, 자세한 분석에는 어느 명령어가 어떤 주소를 읽거나 쓰려 했고 어느 레지스터가 잘못됐을 가능성이 큰지 적습니다. 해제된 메모리로 점프해 튕겼으면 "해제된 메모리(예: 제거된 후킹 코드)로 이동했다"고 씁니다. 레지스터로 다시 계산한 주소가 예외 기록과 맞을 때만 레지스터를 짚고, 모르는 명령어면 아무것도 적지 않습니다.
- **게임 스레드끼리 엔진 잠금에서 서로를 기다리며 멈춘 프리징을 알아봅니다**(`engine_lock_deadlock`). 게임 엔진은 자기 잠금을 기다릴 때 OS 대기 대신 잠깐씩 잠들어서, 지금까지는 Windows 대기 정보(WCT)에 이런 교착이 보이지 않았습니다. 특정 모드를 원인으로 지목하지 않습니다.
  - 1.5.97에서 알려진 교착 3종은 해결 모드를 안내합니다: 셀 로딩 잠금 순서 교착과 읽기/쓰기 잠금 자기 교착은 [Skyrim Cell load Freeze fix NG](https://www.nexusmods.com/skyrimspecialedition/mods/160704), 작업 스레드 스핀 잠금 교착은 [WorkerSpinLockFix](https://www.nexusmods.com/skyrimspecialedition/mods/180884)(`[phase4_defer] enabled=true`).
- **Alt+F4로 게임을 강제 종료하다 난 오류를 CTD로 보고하지 않습니다.** 게임은 Alt+F4를 받으면 렌더러와 모드 DLL을 정리하며 닫히는데, 이때 일부 모드의 후킹 코드가 이미 사라진 뒤에 불려 오류가 나는 경우가 있습니다. 지금까지는 이것이 CTD로 기록되고 뷰어가 자동으로 떴습니다. 이제 플러그인이 Alt+F4·창 닫기(X 버튼)·게임 메뉴의 종료를 기록하고, 그로부터 10초 안에 난 오류는 "강제 종료 중 오류"로 분류합니다. 뷰어가 자동으로 뜨지 않고, 크래시 기록(같은 크래시 횟수, 크래시 버킷)에 넣지 않습니다. 덤프와 리포트는 그대로 남습니다.
- **예전에 분석해 둔 덤프를 뷰어가 자동으로 다시 분석합니다.** 요약에 분석기 버전을 기록하고, 뷰어보다 오래된 분석기가 쓴 요약은 열 때 한 번 다시 분석합니다. v0.2.69에서처럼 분석 버튼을 다시 누를 필요가 없습니다.

## rc3 이후 바뀐 것
- 게임 메뉴에서 종료를 고르면 닫기 요청이 기록되지 않던 문제를 고쳤습니다. rc3는 종료 플래그를 게임 메인 스레드에서 도는 하트비트 작업에서만 읽었는데, 메뉴에서 종료하면 다음 프레임에 메인 루프가 끝나 그 작업이 다시 돌지 않았습니다. 이제 하트비트 스케줄러 스레드가 25ms마다, 그리고 크래시 순간에도 종료 플래그를 읽습니다. 게임이 이미 정리한 메모리여도 오류 없이 읽습니다.
- 일지(시스템 탭)에서 종료하면 "그 밖의 강제 종료"(`forced_quit`)로 분류되던 문제를 고쳤습니다. 일지는 종료 확인을 별도 확인 창이 아니라 일지 안에서 하므로, 일지가 열려 있으면 메뉴의 종료(`game_quit`)로 봅니다.

## 엔진 변경
**플러그인**
- 닫기 요청 기록(`EnableCloseRequestLog=1`, 기본 켬): 스카이림은 키보드를 DirectInput으로 읽어 Alt+F4가 창 메시지로 오지 않으므로, 다음을 함께 봅니다.
  - 하트비트 스케줄러 스레드가 25ms마다 Alt와 F4 키 상태를 읽고, 게임 창이 앞에 있을 때 둘이 함께 눌리면 기록합니다.
  - 크래시 순간에 Alt+F4가 아직 눌려 있으면 기록합니다(Alt+F4를 처리하는 바로 그 프레임에서 난 오류). 이미 GUI 스레드인 스레드에서만 확인합니다.
  - 게임의 종료 플래그(`Main::quitGame`)를 하트비트 스케줄러 스레드가 25ms마다, 그리고 크래시 순간에 읽어 켜지는 순간을 기록하고, 그때 상황으로 Alt+F4, 메뉴의 종료(종료 확인 창·메인 메뉴·콘솔 `qqq`·일지), 그 밖의 강제 종료를 구분합니다. 게임이 정리 중에 이미 해제한 메모리여도 오류 없이 읽습니다(`ReadProcessMemory`).
  - 게임 창 스레드의 관찰 전용 훅(`WH_GETMESSAGE`, `WH_CALLWNDPROC`)으로 X 버튼과 다른 프로그램의 닫기 요청을 봅니다. 메시지를 바꾸지 않고 항상 다음 훅으로 넘기며, 창 프로시저를 서브클래싱하지 않습니다.
  - 처음 본 닫기 요청은 `SkyrimDiag.log`에 한 줄 남깁니다(예: `close request seen: alt_f4 (keys held, game foreground)`).
- 블랙박스 이벤트 `kCloseRequest`(90)를 추가했습니다. 기존 이벤트 해석은 그대로라 공유 메모리 버전은 올리지 않았습니다.

**Helper**
- 프리징·수동 캡처에서 `ntdll!NtDelayExecution`에서 잠든 게임 스레드의 비휘발 레지스터와 스택 위쪽이 가리키는 SkyrimSE.exe 쓰기 가능 데이터를 64바이트 단위로 덤프에 추가하고, 실행 파일 헤더(4KB)도 함께 담습니다. 상한은 스레드당 32개, 전체 128개, 256KB, 20ms이고, 기존 오브젝트 메모리 예산 안에서 씁니다. Helper 로그에 `Lock memory:` 한 줄이 남습니다. 게임 쪽 `NtDelayExecution` 앞부분이 Helper의 것과 다르면 이 수집을 하지 않습니다.
- 닫기 요청 10초 안의 크래시는 뷰어 자동 열기를 건너뛰고 로그에 남깁니다(`Skipped viewer auto-open: crash followed a close request (Alt+F4) …`). 덤프와 자동 분석은 그대로 하고, 크래시 버킷 통계는 갱신하지 않습니다.
- 프리플라이트 경로가 사용자 프로필 폴더 자체면 `<redacted>\<user>`로 가립니다(분석기와 같은 규칙).

**분석기**
- 알려진 크래시: `crash_signatures.json`에 1.6.1170 크래시 지점 8곳을 알려진 원인(`root_cause`)으로 추가했습니다(20개 → 25개). 오프셋은 각 수정 모드 제작자가 공개한 1.6.1170 샘플이고, 명령어는 1.6.1170 덤프 안의 게임 코드와 대조해 모두 맞았습니다. 함정 접촉 크래시 서명 `TRAP_CONTACT_REMOVED_1_6_1170`(크래시 메커니즘, 신뢰도 중간)도 추가했습니다. 크래시 쪽 서명 비교에 로드된 모듈 목록을 넘겨, 수정 모드가 이미 로드된 경우의 안내가 나옵니다.
- 크래시 명령어: 접근 위반이면 예외 위치의 명령어를 해석해 읽기/쓰기/실행, 크기, 주소식을 구하고, 레지스터 값으로 다시 계산한 주소가 예외 기록의 주소와 맞는지 확인합니다. 근거 목록, 리포트 `예외 명령어:` 줄, Summary JSON `fault_instruction`, 빠른 답 `quick_answer.how_it_crashed`에 씁니다. 판정은 null 포인터, 해제됐거나 망가진 포인터, 잘못된 인덱스, 덮어써진 포인터(메모리 손상), 정렬 안 된 SSE 주소, 망가진 스택, 코드가 아닌 곳으로의 호출입니다. `bad_jump`면 대상 주소의 메모리 상태(`fault_instruction.target_state`: `freed`, `reserved`, `not_executable`, `executable`)를 덤프의 메모리 정보에서 읽고, `freed`와 `not_executable`이면 문장을 바꿉니다. 원인 모드 지목, 신뢰도, 알려진 크래시 판정, 버킷은 바뀌지 않습니다. Crash Logger 안에서 난 크래시는 설명을 붙이지 않습니다.
- 엔진 잠금 교착: 잠금 함수 자기 프레임까지의 레지스터·스택 값 중 다른 스레드가 쥔 `BSSpinLock`이나 쓰기로 잡힌 `BSReadWriteLock`을 가리키는 것만 대기로 보고, 대기끼리 고리를 이룰 때만 교착으로 판정합니다(신뢰도 중간). 메인 스레드를 알 수 없는 덤프에서도 게임 스레드를 봅니다. Summary JSON `freeze_analysis.game_lock_waits`, `freeze_analysis.engine_lock_deadlock`, 리포트, 근거, 빠른 답, 버킷(`HANG1-` + 잠금 위치)에 씁니다. 1.5.97 교착 3종은 게임 버전, 스레드별 스택 위치, 잠금 위치와 쥔 스레드가 모두 맞을 때만 일치합니다.
- 강제 종료: 덤프의 블랙박스로 Helper와 같은 판정을 합니다. Summary JSON `analysis.is_forced_close`와 `forced_close`(종류, 닫기 요청에서 크래시까지 걸린 시간), 리포트 분류 줄(`분류: 강제 종료 (CTD 아님; …)`), 근거, `[강제 종료]` 다음 조치에 씁니다. 정상 종료처럼 크래시 이력에서 뺍니다.
- 권고 분류: 권고마다 분류(`immediate`/`verify`/`recapture`)를 Summary JSON `recommendation_classes`에 함께 기록합니다. 기존 `recommendations` 배열은 그대로입니다.
- Summary JSON에 `analyzer_version`을 추가했습니다.
- 경로 가리기: 경로 마스킹이 켜져 있으면(기본값) Crash Logger C++ 예외 메시지, 오류 창 내용, 이를 인용한 근거·권고 문장, WCT 사본 안의 절대 경로도 마지막 이름만 남기고 가립니다. 값이 사용자 프로필 폴더 자체면 `<redacted>\<user>`로 가립니다.
- 리포트의 리소스 로드 시각이 세션 16분쯤부터 `2.91565e+06`처럼 과학적 표기로 나오던 문제를 고쳤습니다.
- 덤프의 WCT 값과 `crash_history.json` 값이 비정상적으로 길어도 분석기가 강제 종료되지 않습니다.

**뷰어**
- 저장된 요약을 다시 쓸지 정하는 규칙: 빠른 답이 없거나, 분석기 버전이 없거나 뷰어보다 낮으면 다시 분석합니다. 더 새 분석기가 쓴 요약은 그대로 보여 줍니다.
- 빠른 답 카드와 요약 복사·공유 텍스트에 "어떻게 튕겼나" 줄을 보여 줍니다. 빠른 답 카드의 줄을 항목마다 따로 채워, "해볼 일"이 없는 답에서 다음 줄이 엉뚱한 칸에 들어가지 않습니다.
- 강제 종료 중 오류는 분류와 공유 텍스트 머리글에 강제 종료로 표시합니다.
- 권고를 "지금 바로 / 추가 확인 / 재수집 / 비교"로 묶을 때 표시 문구 대신 분석기가 적은 분류를 씁니다. "[프리징] … 다시 캡처" 권고가 영어 화면에서만 "추가 확인"으로 묶이던 문제를 고쳤습니다.

**CI·개발**
- Linux 빌드의 패키지 설치가 미러 문제로 멈추면 다시 시도하고 시간 제한을 둡니다.
- `scripts/compare_analyses.py`: 두 분석기 빌드를 같은 덤프로 돌려 사용자가 보는 내용의 차이만 보여 주는 도구.

## 실게임에서 확인한 것
- 1.6.1170(MO2, 켜진 모드 약 4,360개, Crash Logger 1.25)에서:
  - 잠금 메모리 수집(rc2와 같은 코드의 시험 빌드): 수동 캡처에서 `Lock memory: threads=4 pointers=4 ranges=3 bytes=4224 time_us=375`, 실행 파일 헤더와 데이터 조각이 덤프에 들어감, 캡처 뒤 게임 정상, 종료 코드 0.
  - 강제 종료 구분이 생긴 계기: PrismaUI 테스트 빌드가 Alt+F4 때마다 해제된 후킹 코드를 불러 오류를 냈고, rc2는 이것을 CTD로 기록하고 뷰어를 띄웠습니다(2026-10-26).

## 주의사항
- 다른 창·오버레이 모드와 충돌이 의심되면 `SkyrimDiag.ini`의 `EnableCloseRequestLog=0`으로 닫기 요청 기록을 끌 수 있습니다. 끄면 Alt+F4 뒤의 오류도 예전처럼 CTD로 보고합니다.
- 닫기 요청 뒤 10초 안에 난 오류는 모두 강제 종료 중 오류로 봅니다. 게임이 닫기 요청을 무시하고 계속 돌다가 10초 안에 진짜 CTD가 나면 그것도 강제 종료로 분류됩니다.
- 콘솔이나 메인 메뉴, 일지, 종료 확인 창을 연 채로 누른 Alt+F4를 키 샘플이 놓치면 "게임 종료를 고른 뒤…"로 나옵니다.
- Engine Fixes의 safe exit처럼 종료를 고르자마자 프로세스를 끝내는 환경에서는, 메뉴로 종료해 오류 없이 꺼졌을 때 `SkyrimDiag.log`에 닫기 요청 줄이 남지 않을 수 있습니다. 종료 중 오류가 나면 오류 순간에 종료 플래그와 열린 메뉴를 다시 읽으므로 분류에는 영향이 없습니다.
- 알려진 엔진 잠금 교착 3종의 해결 모드 안내는 1.5.97에만 있습니다. 1.6.x에서 같은 형태의 교착이 나면 해결 모드 이름 없이 엔진 잠금 교착으로만 보고합니다. 게임이 정상일 때의 수동 캡처에는 교착 판정을 하지 않습니다.
