# v0.2.60 — 프리징 리포트가 메인 스레드의 대기를 설명

v0.2.60-rc1부터 rc5까지의 변경을 묶은 정식 릴리즈입니다. 기존 파일 일부만 덮지 말고 ZIP 전체를 설치해 주세요.

## 핵심 변경
- **프리징 리포트가 메인 스레드의 대기를 설명** — 멈춘 메인 스레드가 무엇을 하고 있었는지 분류합니다: 게임 엔진 안의 대기, 플러그인이 부른 대기, 그래픽 드라이버 안의 대기, 코드 실행 중. 엔진이 Direct3D 쿼리(`ID3D11DeviceContext::GetData`) 결과를 `Sleep` 루프로 기다리는 GPU 대기는 덤프에 남은 실행 코드의 모양으로 알아봅니다.
  - 보관 중인 실사고 프리징 5건은 모두 GPU 쪽 대기였습니다(엔진의 쿼리 대기 4건, NVIDIA 드라이버 안의 대기 1건). 이전 리포트는 4건에서 CommunityShaders를, 1건에서 FSMP를 근거 없이 후보로 올렸습니다.
  - 이제 엔진·드라이버 대기에서는 스택의 플러그인을 후보로 올리지 않고, GPU 쪽 점검(드라이버, 감지된 ENB·ReShade·DXVK, 업스케일러, 비디오 메모리)을 다음 조치로 안내합니다. 데드락, 동기화 정지, 로더 stall 판정이 있으면 그 안내가 먼저입니다.
- **캡처 당시 게임 상태** — 열려 있던 게임 메뉴(예: 콘솔), 마지막 로딩 뒤 지난 시간, 직전의 5분 이상 정지(PC 절전이나 최소화로 추정)를 요약 문장과 근거 항목에 적습니다.
- **플러그인 오류 창 안내** — 플러그인이 띄운 CommonLib Address Library 오류 창 때문에 게임이 멈추면, 그 플러그인이 현재 게임 버전을 지원하지 않는지 Address Library가 없는지 구분해 무엇을 바꿔야 하는지 안내합니다.
- **SKSE가 정상적으로 로드하지 못한 DLL** — 그 실행의 skse64.log(게임 EXE 기준 주소로 같은 실행인지 확인)를 읽어, 로드되지 못한 DLL과 사유를 같은 사유끼리 묶어 참고 정보로 보여 줍니다. 원인 후보로는 쓰지 않습니다.
- **AMX CPU에서 CTD 덤프 쓰기 실패 수정** — Windows Server 2022의 dbghelp는 AMX가 있는 CPU에서 예외 컨텍스트를 확장 상태 크기(약 11.5KB)만큼 읽는데, Helper가 넘기던 것은 1,232바이트 `CONTEXT`였습니다. 이제 확장 상태 크기 버퍼에 담아 넘깁니다.
- **Helper 안정성** — `é` 같은 문자가 든 플러그인 이름 때문에 Helper가 종료돼 프리징 덤프를 잃던 문제를 고쳤습니다. 게임을 다시 켜도 직전 세션의 로그가 `SkyrimDiagHelper.previous.log`로 남고, 관리자가 아닌 사용자에게 매번 찍히던 `EnableDebugPrivilege failed` 경고를 없앴습니다.
- **다음 조치** — 리포트의 `NextAction`을 태그 우선순위(modal 대화상자·메인 스레드 → 행동 우선 후보 → Crash Logger 프레임 → 오브젝트 참조 → 충돌)로 고르고, WinUI 화면과 공유 텍스트도 같은 줄을 씁니다. 실사고 CTD 5건 모두 설명이나 일반 문구 대신 실제 후보를 가리킵니다.

## 엔진 변경
- 분석기: 프리징 캡처의 메인 스레드 콜스택을 0번 프레임부터 16개 보여 줍니다. 크래시 콜스택과 crash bucket 키는 그대로입니다.
- 분석기: 요약 JSON에 `freeze_analysis.main_thread_wait`, `freeze_analysis.game_state`, `freeze_analysis.modal_dialog_wait.address_library_issue`, `plugin_scan.skse_log`, `next_action_index`를, 리포트에 `main_thread_wait`, `game_state`, `SkseLog:`(한국어 리포트는 `SKSE 로그:`) 줄을 추가했습니다.
- 분석기: 게임 상태의 시간은 메인 스레드의 마지막 하트비트(프리징이 시작된 때)까지 잽니다. 리포트 줄과 근거 문장 모두 초를 반올림합니다(rc5에서는 리포트 줄만 버려서 1초 다르게 나왔습니다).
- Helper: `plugins.txt`, `Skyrim.ccc`, 플러그인 헤더의 마스터 이름, skse64.log를 ANSI 코드 페이지에서 UTF-8로 바꿔 다루고, 스캔이나 SKSE 로그 읽기가 실패해도 캡처를 계속합니다.
- Helper: 덤프가 실패하면 오류를 16진수로도 적고, 로드된 dbghelp.dll의 버전과 경로를 남깁니다.
- Helper: 보관 정리가 어떤 파일 이름에서도 예외로 멈추지 않습니다.
- CI: 문서만 바꾼 PR은 Windows job을 건너뜁니다(main 푸시와 릴리즈는 항상 전체 실행). Windows 빌드의 일시적 링크 실패는 한 번 다시 빌드하고, skse64.log 파서 퍼저를 Linux fuzz 스모크에 추가했습니다.

## 실게임에서 확인한 것
- rc1~rc5를 한 사용자의 MO2 환경(게임 1.6.1170, SKSE 2.2.6)에서 수동 캡처로 확인했습니다.
- 확인됨: skse64.log 매칭(`SKSE log: matched (checked=325, loaded=323, not_loaded=2)`)과 `[SKSE]` 안내, 같은 사유 DLL 묶기, 수동 캡처와 576~581MB 덤프·정상 종료, 권한 경고 없음, `SkyrimDiagHelper.previous.log` 유지, 하트비트 기준 "마지막 로딩 뒤 지난 시간".
- 보관 덤프 재분석으로만 확인: 새 프리징 분석(실사고 프리징 5건과 modal 1건), Address Library 오류 창 안내(SmoothCam), 실사고 CTD 5건의 다음 조치.
- 실게임 미확인: 새 프리징 분석이 실제 프리징 캡처에서 나오는지, 모드의 assert로 난 CTD에서 `ExceptionCode`가 `0x80000003`인지, 덤프 실패 시 실패 위치 진단, AMX CPU에서의 CTD 덤프(CI에서만 확인).

## 정정
- v0.2.59 정식 노트는 CI의 간헐적 덤프 실패를 `ERROR_PARTIAL_COPY`로 설명하고 "원인은 아직 모른다"고 했습니다. 실제 오류는 `0x800706F8`(ERROR_INVALID_USER_BUFFER)였고, 원인은 AMX CPU에서 dbghelp가 예외 컨텍스트를 확장 상태 크기만큼 읽은 것이었습니다(rc3에서 수정, 수정 뒤 AMX 호스트 4대를 포함한 48개 job 통과).
- rc1 노트는 "거부된 DLL은 실행되지 않으므로"라고 했지만, "crashed during postload"처럼 DLL 코드가 이미 실행된 상태도 목록에 나옵니다. 이제 "정상적으로 로드하지 못한 DLL"로 적습니다. 원인 후보로 쓰지 않는 원칙은 같습니다.
- rc4 노트는 "WinUI도 같은 줄을 씁니다"라고 했지만, 후보나 충돌 안내가 있으면 WinUI가 다른 줄을 고를 수 있었습니다. rc5에서 고쳤습니다.

## 주의사항
- 플러그인 코드는 v0.2.59와 같지만 Helper, 분석기, WinUI가 바뀌었고 버전 정보도 바뀌었습니다. ZIP 전체를 교체해 주세요. 공유 메모리 프로토콜(SharedLayout v4)은 v0.2.59와 같습니다.
- GPU를 기다렸다는 것까지만 알려 주고, GPU가 왜 끝내지 못했는지(어느 셰이더나 그리기 작업인지)는 덤프로 알 수 없습니다.
- 게임 EXE가 플러그인이 잡은 잠금에서 기다리는 경우도 "엔진 안의 대기"로 분류될 수 있습니다. 이때 스레드 그룹 합의가 없으면 그 플러그인은 후보에서 빠집니다.
- ENB의 `d3d11.dll`, ReShade의 `dxgi.dll` 같은 프록시 DLL 안에서 기다려도 "그래픽 드라이버 안에서 대기"로 나옵니다(안내에는 감지된 인젝터를 적습니다).
- skse64.log 형식은 1.6.1170의 SKSE 2.2.6으로만 확인했습니다. `msdia140.dll`처럼 SKSE 플러그인이 아닌 보조 DLL도 목록에 나옵니다.
- 한국어 리포트의 일부 후보 안내 문장에는 아직 영어 용어가 섞여 있습니다.
- 검수된 실사고 코퍼스가 없어 다른 크래시 로거 대비 적중률을 수치로 주장하지 않습니다.
