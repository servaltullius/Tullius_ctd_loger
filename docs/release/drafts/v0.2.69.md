# v0.2.69 — 쉬운 말 빠른 답, 프리징 원인 판정 보강(잠금 주인, Crash Logger 교착, 엔진 NaN 반복), 오브젝트 단서

v0.2.69-rc1~rc3를 묶어 정식으로 내는 릴리즈입니다. rc3 이후 코드는 바뀌지 않았습니다. Helper와 분석기, 뷰어가 바뀌었으니 ZIP 전체를 설치해 주세요. MO2에서 새 모드로 설치했다면 이전 버전 모드는 꺼 주세요.

## 한눈에 보기
- **리포트와 뷰어가 쉬운 말로 된 "빠른 답"으로 시작합니다.** 넥서스 사용자 피드백(리포트가 너무 어렵다, 원인 모드를 바로 알려 달라)을 반영했습니다. 무슨 일이 있었는지, 의심되는 모드(MO2 모드 이름)와 그 가능성(높음/중간/낮음), 해볼 일 한 가지, 확실하지 않으면 그 이유를 3~4줄로 먼저 보여 주고, 자세한 분석은 그 아래에 둡니다.
- **프리징 원인을 더 정확히 짚습니다.**
  - 메인 스레드가 다른 스레드가 쥔 잠금을 기다리다 멈추면 그 스레드를 찾아 알려 줍니다(`lock_owner_wait`).
  - Crash Logger 스레드 덤프 단축키가 게임을 교착시킨 경우를 알아봅니다(`crash_logger_thread_dump_deadlock`).
  - 게임 계산 값이 숫자가 아닌 값(NaN)이 되어 엔진이 같은 계산을 끝없이 반복하다 멈춘 경우를 알아봅니다(`engine_spin_nan`). 1.6.1170의 알려진 AI 길찾기 프리징이면 [AI Pathing Freeze Fix](https://www.nexusmods.com/skyrimspecialedition/mods/190049) 설치를 안내합니다.
  - 오류 창 때문에 멈추면 창 제목에 적힌 모드 이름으로 원인 모드를 짚습니다.
- **엉뚱한 모드를 덜 지목합니다.** 메인 스레드나 멈춘 게임 스레드의 스택 깊은 곳에 있을 뿐인 플러그인(업스케일러, FSMP 등)을 원인으로 내세우지 않고 "호출 경로에 있었을 뿐"으로 적습니다.
- **프리징 덤프에 멈춘 스레드가 다루던 게임 오브젝트를 담습니다.** 이후 프리징에서는 "멈춘 계산이 다루던 대상: Character "이름" (FormID …, 플러그인)" 같은 단서를 볼 수 있습니다.

## 엔진 변경
**분석기**
- 빠른 답: Summary JSON `quick_answer`, 리포트 맨 위 "빠른 답" 블록과 "자세한 분석" 구분선. 외부 프로그램, 알려진 해결 방법, 프리징 종류, 오류 창, 로딩, 스냅샷마다 맞는 조치. 많은 모드가 기대는 모드(Engine Fixes, FSMP)는 "업데이트, 끄는 것은 시험할 때만"으로 안내합니다.
- 잠금 주인: WCT 사슬을 끝 스레드까지 따라가고, 두 패스가 같은 스레드를 가리킬 때만 확인된 주인으로 봅니다. 다른 프로세스나 덤프에 없는 스레드는 주인으로 보지 않습니다. 스레드 이름(ThreadNamesStream)을 읽어 표시합니다.
- Crash Logger 스레드 덤프 교착: Crash Logger 코드 안의 스레드, 밖에서 멈춰진 잠금 주인, 중간에 끊긴 스레드 덤프 로그가 함께 보이고, 게임이 스레드 덤프가 시작된 뒤에 멈췄을 때만 판정합니다. 조언은 단축키를 쓰지 않거나 끄는 것 하나입니다.
- 엔진 NaN 반복: 대상 스레드가 WCT 두 번 모두 실행 중이고, 게임 실행 파일의 부동소수점 비교 루프에서 비교 값이 NaN이면 판정합니다. 특정 모드를 지목하지 않습니다.
- 알려진 해결 방법에 프리징용 조건(게임 버전, 판정, 루프 위치)을 추가하고 AI 길찾기 프리징을 등록했습니다. 해결 모드가 이미 로드돼 있으면 업데이트 확인을 안내합니다.
- 오류 창 원인 모드: 창 제목, 없으면 본문에서 로드된 모드 DLL 이름을 찾아 하나만 걸리면 지목합니다.
- 호출 경로: 메인 스레드가 기다린 게임 스레드가 엔진 코드를 실행 중이고 플러그인이 그 아래 5프레임 이상 깊이에만 있으면 원인 후보에서 뺍니다.
- 프리징 버킷: 잠금 대기는 주인 스레드로, 교착은 판정 하나로, NaN 반복은 루프 위치로 묶어 일반 그래픽 드라이버 대기와 섞이지 않습니다(버킷 버전은 그대로 3).
- 프리징 오브젝트: 메인·잠금 주인·실행 중·판정이 가리키는 스레드의 오브젝트를 `freeze_analysis.thread_objects`와 리포트, 빠른 답 단서로 보여 줍니다. 판정·신뢰도·후보는 바뀌지 않습니다.

**Helper**
- 프리징·수동 캡처에서 메인 스레드, WCT 대기 사슬, 실행 중 스레드(최대 16개)의 레지스터와 스택이 가리키는 오브젝트 메모리를 덤프에 추가합니다. 덤프를 쓰려고 스레드를 이미 멈춘 동안 읽고, 커밋되고 읽을 수 있는 페이지만 읽습니다. 상한 4MB(스레드당 1MB), 100ms. Helper 로그에 `Object memory:` 한 줄이 남습니다.
- 크래시 덤프를 다시 시도할 때 추가 메모리 범위가 빠지던 문제를 고쳤습니다.

**뷰어**
- 빠른 답 카드를 요약 카드 위에 보여 주고, 요약 복사·공유 텍스트가 빠른 답으로 시작합니다.

## 실게임에서 확인한 것
- 1.6.1170(MO2, 켜진 모드 약 4,360개, Crash Logger 1.25)에서:
  - v0.2.68 프리징 두 번(같은 화이트런 실내 로딩 직후): 덤프로 엔진 NaN 반복과 호출 경로의 업스케일러를 확인했고, AI Pathing Freeze Fix 설치 뒤 다시 나지 않았습니다.
  - rc3 수동 캡처: `Object memory: threads=16/16 … bytes=12824 time_us=8851`(12.8KB, 8.9ms), 덤프 크기 그대로, 캡처 뒤 게임 정상, 종료 코드 0.
  - rc3 세션: 처리된 접근 위반이 `SkyrimDiag_Released_*.dmp`로 보관됐다가 게임이 1분 넘게 돌자 지워졌고, 종료 때 다시 보고되지 않았습니다.
- 실게임 미확인: 실제 프리징에서 빠른 답의 오브젝트 단서, 실제 Crash Logger 교착에서의 새 판정(2026-10-18 덤프로 확인), 잠금 대기 판정. 모두 실제 덤프 재분석과 런타임 테스트로 확인했습니다.

## 정정
- rc3 노트는 "수동 캡처 리포트의 `thread_objects` 줄"을 확인하라고 했지만, 이 줄은 게임이 멈춘 캡처에서만 나옵니다. 게임이 정상으로 돌 때의 수동 캡처에는 없는 것이 정상입니다.

## 주의사항
- 이전 덤프에는 게임 힙이 없어 오브젝트 단서는 새 캡처부터 나옵니다.
- 원인 오브젝트를 더 확실히 보고 싶으면 `SkyrimDiagHelper.ini`에서 잠시 `DumpMode=2`(전체 메모리)로 재현할 수 있습니다(덤프가 수 GB로 커짐).
- 빠른 답은 쉬운 말로 줄인 결과입니다. 단정하기 어려운 경우에는 "확실하지 않은 이유"를 함께 적으니 그 줄도 읽어 주세요.
